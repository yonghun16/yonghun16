## 개요
메뉴 등록·삭제([[메뉴등록]], [[메뉴삭제]])에 이어 **메뉴 정보 수정,
품절 처리, 순서 변경 모두 완료**됐습니다. 수정 이력(누가 언제 무엇을
바꿨는지) 관리는 이번 범위에 넣지 않았습니다.

## 완료: 메뉴 수정
관리자 화면의 메뉴 목록에서 각 항목의 "수정" 버튼을 누르면 **모달**이
뜨고, 그 안에서 이름·가격·이미지(파일 재업로드 가능)·카테고리를 고쳐서
저장할 수 있습니다. "취소"를 누르거나 저장에 성공하면 모달이 닫힙니다.

처음엔 목록의 그 항목 자리가 그대로 편집 폼으로 바뀌는 인라인 방식이었는데,
[[메뉴등록]]을 모달로 바꾼 것과 같은 이유로(목록을 더 넓게, 화면을 덜
복잡하게) 모달 방식으로 통일했습니다. `shared/ui/Modal`을 그대로
재사용합니다.

### 관련 코드
- `apps/frontend/src/widgets/manage-product-list/ui/EditProductForm.tsx`
  (폼 자체 — 카드 껍데기 없이 `Modal`에 감싸여 쓰임)
- `apps/frontend/src/widgets/manage-product-list/ui/ManageProductList.tsx`
  (수정 버튼 → `editingProductId` 상태 → `Modal` 열림/닫힘)
- `apps/frontend/src/shared/ui/Modal.tsx` (범용 모달)
- `apps/frontend/src/features/product-management/model/store.ts`
  (`editProduct` 액션)
- `apps/frontend/src/entities/product/api/productApi.ts`
  (`updateProduct`)
- `apps/backend/src/routes/products.ts` — `PUT /api/products/:id`
  (`requireAdmin`으로 보호)

## 완료: 품절 처리
메뉴 목록의 각 항목에 "품절 처리"/"판매 재개" 버튼이 있어 클릭 한 번으로
`Product.isSoldOut` 값을 토글합니다. 관리자 목록에서는 품절 항목이
흐리게 표시되고 "품절" 배지가 붙습니다. 고객 화면(`/`)에서도 품절
메뉴는 흑백 처리 + "품절" 배지로 표시되며, 클릭해도 장바구니에 담기지
않고 "품절된 메뉴입니다" 안내만 뜹니다.

수정 이력(누가 언제 품절/수정 처리를 했는지) 관리는 이번 범위에
넣지 않았습니다 — 필요해지면 별도로 논의합니다.

### 관련 코드
- `apps/backend/src/models/Product.ts` (`isSoldOut` 필드, 기본값 `false`)
- `apps/backend/src/routes/products.ts` — `PATCH /api/products/:id/sold-out`
  (`requireAdmin`으로 보호)
- `apps/frontend/src/entities/product/api/productApi.ts`
  (`updateSoldOutStatus`)
- `apps/frontend/src/entities/product/ui/ProductCard.tsx` (고객 화면
  품절 표시 및 담기 차단)
- `apps/frontend/src/widgets/manage-product-list/ui/ManageProductList.tsx`
  (관리자 목록의 품절 처리/판매 재개 버튼)
- `apps/frontend/src/features/product-management/model/store.ts`
  (`toggleSoldOut` 액션)
- `packages/types`의 `UpdateSoldOutInput`

## 완료: 메뉴 순서 변경
[[카테고리관리]]의 카테고리 순서 변경과 같은 방식으로, 메뉴도 **같은
카테고리 안에서** 드래그하거나 ▲▼ 버튼으로 순서를 바꿀 수 있습니다.
순서는 카테고리 안에서만 의미가 있어서, "메뉴 관리" 탭에서 "전체"가
아니라 **특정 카테고리를 골랐을 때만** 드래그 손잡이(⠿)와 ▲▼ 버튼이
나타납니다. 이 순서는 고객 화면(`/`)의 메뉴 목록에도 그대로 반영됩니다.

카테고리 드래그 때와 마찬가지로 브라우저 네이티브 HTML5 드래그가 아니라
**포인터 이벤트 기반 커스텀 드래그**로 구현했습니다 — 손잡이에서
`pointerdown`으로 시작해 `window`의 `pointermove`로 좌표 hit-test하며
화면만 즉시 재배치하다가(`reorderLocally`, API 호출 없음), `pointerup`
에서 한 번만 서버에 저장합니다(`commitProductOrder`).

`PATCH /api/products/reorder`는 **같은 카테고리에 속한** 상품 id를
원하는 순서대로 나열한 배열을 받아 배열 인덱스를 그대로 `order` 값으로
저장합니다(카테고리 순서 API와 동일한 방식). 새 메뉴는 그 카테고리 안에서
항상 맨 뒤 순서로 등록됩니다. `order` 필드가 생기기 전에 이미 있던
메뉴는 서버 시작 시 카테고리별로 생성순 그대로 순서를 자동 부여합니다
(`ensureProductOrder`, 1회성·멱등).

### 관련 코드
- `apps/backend/src/models/Product.ts` (`order` 필드)
- `apps/backend/src/routes/products.ts` — `PATCH /api/products/reorder`
  (`requireAdmin`으로 보호), `GET /api/products`가
  `category → order` 순으로 정렬
- `apps/backend/src/lib/seed.ts` — `ensureProductOrder`(자동 시딩)
- `apps/frontend/src/entities/product/api/productApi.ts`
  (`reorderProducts`)
- `apps/frontend/src/features/product-management/model/store.ts`
  (`moveProduct`/`reorderLocally`/`commitProductOrder`, 전부 같은
  카테고리 안에서만 재배치)
- `apps/frontend/src/widgets/manage-product-list/ui/ManageProductList.tsx`
  (드래그 손잡이 + ▲▼ 버튼, `selectedCategory !== 'all'`일 때만 표시)
- `packages/types`의 `Product.order`, `ReorderProductsInput`
