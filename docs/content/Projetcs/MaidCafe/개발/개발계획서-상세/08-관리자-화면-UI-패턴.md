## TL;DR
관리자 화면(`/admin`)에는 라이브러리 없이 직접 구현한 UI 패턴이
세 가지 반복해서 등장합니다: (1) 포인터 이벤트로 만든 드래그 순서
변경, (2) SVG로 직접 그린 매출 꺾은선 그래프, (3) 스크롤 부모의
클리핑을 피하는 포털(Portal) 기반 드롭다운. 세 개 다 "필요한 게
작고 명확해서, 무거운 라이브러리(react-beautiful-dnd, chart.js
등)를 추가하는 것보다 직접 짜는 게 더 간단하다"는 판단으로
만들었습니다.

## 1. 포인터 이벤트 기반 드래그 재배치

카테고리 칩([[카테고리관리]]), 광고 목록([[광고관리]]), 특정
카테고리로 필터링된 상품 목록에서 드래그로 순서를 바꿀 수 있습니다.
전부 같은 알고리즘을 씁니다.

### 왜 HTML5 네이티브 드래그(`draggable` 속성)가 아닌가
네이티브 드래그 앤 드롭은 칩/카드 안에 버튼이 여러 개 겹쳐 있으면
(수정 버튼, 삭제 버튼 등) 브라우저/기기에 따라 **드래그 시작 자체가
인식되지 않는** 경우가 있습니다. 특히 터치 기기에서 이 문제가
두드러집니다. 그래서 포인터 이벤트(mouse/touch/pen을 하나의 API로
통합한 표준)를 전용 손잡이(⠿ 아이콘)에서만 시작하도록 직접
구현했습니다 — 손잡이 밖을 눌렀을 땐 드래그가 시작되지 않으니
버튼 클릭과 충돌하지 않습니다.

### 알고리즘 3단계

```
1. onPointerDown(id)         → draggedId 상태에 저장, 이 시점부터 감시 시작
2. window.pointermove         → 포인터 좌표가 "어느 칩의 사각형 안에 들어왔는지" hit-test
                                → 들어온 칩이 있으면 그 칩의 인덱스로 즉시 재배치(reorderLocally)
3. window.pointerup/cancel    → draggedId를 비우고, 최종 순서를 서버에 저장(commitCategoryOrder)
```

**hit-test(충돌 판정)**: 각 칩의 DOM 엘리먼트를 `useRef<Map<string,
HTMLDivElement>>`에 모아두고, `pointermove`가 일어날 때마다
`getBoundingClientRect()`로 각 칩의 화면상 사각형을 구해 포인터
좌표가 그 안에 있는지 확인합니다.

```ts
chipRefs.current.forEach((el, id) => {
  const rect = el.getBoundingClientRect();
  if (e.clientX >= rect.left && e.clientX <= rect.right &&
      e.clientY >= rect.top && e.clientY <= rect.bottom) {
    hoveredId = id;
  }
});
```

**왜 `window`에 리스너를 다는가(칩 자신이 아니라)**: 드래그 중에는
포인터가 원래 눌렀던 칩 밖으로 자유롭게 움직입니다. 이벤트를
개별 칩에 걸면 포인터가 그 칩 영역을 벗어나는 순간 이벤트를 못
받습니다. `window` 전역에 걸어야 화면 어디로 움직이든 계속 추적할
수 있습니다. 드래그가 끝나면(`pointerup`) 반드시 리스너를 정리해서
(`removeEventListener`) 드래그하지 않을 때는 불필요한 이벤트 감시가
없게 합니다.

### 상태 갱신 — "낙관적 업데이트(optimistic update)"

```ts
reorderLocally: (categoryId, toIndex) => {
  const reordered = reorderArray(get().categories, categoryId, toIndex);
  if (!reordered) return;
  set({ categories: reordered });   // 서버 응답을 기다리지 않고 즉시 화면 갱신
},
commitCategoryOrder: async () => {
  try {
    await reorderCategories(categories.map((c) => c._id));  // 드롭 시점에 한 번만 저장
  } catch (error) {
    get().fetchCategories();   // 저장 실패 시 서버의 진짜 순서로 되돌림(롤백)
  }
},
```

드래그 중 매 프레임마다 서버에 저장 요청을 보내면 네트워크가
감당하지 못합니다. 그래서 **화면 상태만 즉시 바꾸는 함수**
(`reorderLocally`, API 호출 없음)와 **실제로 저장하는 함수**
(`commitCategoryOrder`, 드롭한 순간 딱 한 번)를 분리했습니다. 저장이
실패하면 `fetchCategories()`로 서버의 실제 순서를 다시 받아와서
화면을 원래대로 되돌립니다 — "일단 성공한 것처럼 보여주고, 실패하면
되돌린다"는 낙관적 업데이트 패턴입니다.

**배열 재배치 자체**(`reorderArray`)는 흔한 "splice-out,
splice-in" 방식입니다:

```ts
function reorderArray(items, id, toIndex) {
  const fromIndex = items.findIndex((item) => item._id === id);
  if (fromIndex === -1 || toIndex < 0 || toIndex >= items.length || fromIndex === toIndex) return null;
  const reordered = [...items];
  const [moved] = reordered.splice(fromIndex, 1);   // 원래 자리에서 빼고
  reordered.splice(toIndex, 0, moved);              // 새 자리에 끼워 넣음
  return reordered;
}
```

**서버 저장 — "배열 인덱스를 그대로 order 값으로"**:

```ts
await Promise.all(
  orderedIds.map((id, index) => Category.updateOne({ _id: id }, { $set: { order: index } })),
);
```
프론트엔드가 원하는 순서대로 정렬한 id 배열을 통째로 보내면, 백엔드는
그 배열의 인덱스(0, 1, 2, ...)를 그대로 각 문서의 `order` 필드에
씁니다. "몇 번째 항목을 몇 번째로 옮겼는지"를 따로 계산할 필요 없이,
**최종 순서 자체**를 전송하는 단순한 계약입니다.

## 2. 외부 차트 라이브러리 없는 SVG 꺾은선 그래프

[[매출통계대시보드]]의 월별 판매량 추이 그래프는 chart.js나
recharts 같은 라이브러리 없이 SVG를 직접 그립니다. 데이터 포인트가
많아야 12개(1~12월)뿐이고 필요한 시각화도 단순한 선+점이라, 무거운
차트 라이브러리의 학습/번들 크기 비용이 직접 구현보다 크다고
판단했습니다.

### 좌표 변환 수식
데이터는 "몇 월에 몇 개 팔렸는지"라는 숫자일 뿐, 화면 좌표가
아닙니다. 이걸 SVG 좌표로 바꾸는 게 핵심입니다:

```ts
const maxQuantity = Math.max(1, ...summary.map((row) => row.totalQuantity));
const points = summary.map((row, index) => {
  const ratio = index / (summary.length - 1);        // 0(1월) ~ 1(12월)로 정규화
  return {
    x: CHART_PADDING_X + ratio * PLOT_WIDTH,           // 가로: 그린 영역 안에서 월 순서대로 균등 배치
    y: BASELINE_Y - (row.totalQuantity / maxQuantity) * PLOT_HEIGHT,  // 세로: 값이 클수록 위로
  };
});
```

- **x좌표**: 12개월을 그래프의 가로 폭(`PLOT_WIDTH`)에 균등하게
  펼칩니다. `index / (length - 1)`로 0~1 사이 비율을 구하고, 거기에
  폭을 곱해 실제 픽셀 위치를 얻습니다.
- **y좌표**: SVG는 **위쪽이 y=0**이고 아래로 갈수록 값이 커지는
  좌표계입니다(수학 그래프와 반대). 그래서 "값이 클수록 화면
  위쪽"으로 그리려면 `바닥선(BASELINE_Y) - 비율 × 높이`처럼 **빼는
  방향**으로 계산해야 합니다. 이 부호를 반대로 하면 그래프가 거꾸로
  뒤집혀 그려지는 흔한 실수가 납니다.
- **`Math.max(1, ...)`로 0 나누기 방지**: 판매 데이터가 전부 0이면
  (예: 아직 주문이 없는 미래 연도) `maxQuantity`가 0이 되어 나눗셈이
  `NaN`이 될 수 있습니다. 최솟값을 1로 보정해 이 경우에도 그래프가
  깨지지 않게 합니다.

### 실제 그리기 — `<polyline>` + `<circle>`
점들을 `"x1,y1 x2,y2 ..."` 형태의 문자열로 이어붙이면
`<polyline points="...">` 하나로 전체 꺾은선이 그려집니다. 각 점
위에는 클릭 가능한 `<circle>`을 얹어 그 달의 판매 순위를 조회하는
트리거로 씁니다 — 실제 보이는 원(반지름 5~7px)보다 훨씬 넓은
투명한 원(반지름 20px)을 하나 더 겹쳐서, 손가락/마우스로 정확히
점 중앙을 안 눌러도 클릭이 인식되도록 클릭 판정 영역을 넓혔습니다.

## 3. 스크롤 클리핑을 피하는 포털 드롭다운

`shared/ui/Dropdown.tsx`는 온도/마법의 주문 같은 선택지를 고르는
커스텀 드롭다운입니다. 네이티브 `<select>`를 안 쓴 이유는 모바일에서
OS 기본 선택 UI(iOS 하단 휠, 안드로이드 바텀시트)가 열려 앱
디자인과 어울리지 않기 때문입니다.

### 겪었던 문제 — `overflow-y-auto` 부모 안에서 잘림
처음엔 트리거 버튼 바로 아래에 `position: absolute`로 펼침 목록을
붙였습니다. 이 드롭다운이 [[상품옵션선택]] 모달처럼
`overflow-y-auto`로 스크롤되는 부모 안에서 쓰이면, 펼쳐진 목록이
그 부모의 **스크롤 경계에서 잘려 보이는** 문제가 있었습니다 — 모달
박스를 아무리 키워도 내용이 그보다 많아지는 순간 다시 재현되는
근본적인 문제였습니다(`overflow: hidden/auto`인 조상은 그 안의
`position: absolute` 자손을 자신의 경계 밖으로 못 나가게 자르기
때문).

### 해결 — `position: fixed` + `createPortal`
```ts
const handleToggle = () => {
  const rect = buttonRef.current.getBoundingClientRect();
  setPosition({ top: rect.bottom + 4, left: rect.left, width: rect.width });
  setIsOpen(true);
};
// ...
createPortal(
  <div style={{ position: 'fixed', top: position.top, left: position.left, width: position.width }}>
    {options.map(...)}
  </div>,
  document.body,   // 트리거 버튼의 실제 DOM 위치가 아니라 body 바로 아래에 렌더링
)
```

`createPortal`은 React 컴포넌트 트리(부모-자식 관계)는 그대로
유지하면서, **실제 DOM 위치만** `document.body` 바로 아래로
옮깁니다. `document.body`는 모달의 `overflow-y-auto` 스크롤
컨테이너 바깥에 있으므로, 더 이상 그 스크롤 경계에 잘리지 않습니다.
대신 화면상 위치는 `position: fixed` + `getBoundingClientRect()`로
직접 계산한 좌표로 맞춰서, 마치 트리거 버튼 바로 아래에 붙어있는
것처럼 보이게 합니다.

**대가로 감수한 것**: 포털로 빼낸 목록은 이제 트리거 버튼의 DOM상
자손이 아닙니다. 그래서
1. **"바깥 클릭 감지"**가 트리거 버튼의 `containerRef`뿐 아니라
   포털 목록의 `listRef`도 함께 확인해야 합니다 — 안 그러면 옵션을
   누르자마자 `mousedown` 시점에 "바깥을 눌렀다"고 오판해 먼저
   닫혀버립니다.
2. **위치가 스크롤/리사이즈에 따라 어긋날 수 있습니다** — 부모가
   스크롤되거나 창 크기가 바뀌면 `getBoundingClientRect()`로 계산해둔
   좌표가 낡은 값이 됩니다. 위치를 매번 재계산하는 대신, 스크롤/
   리사이즈가 감지되면 그냥 드롭다운을 닫아버리는 단순한 방법을
   택했습니다(`capture: true`로 등록해 어떤 조상 요소가 스크롤되든
   버블링 없이도 감지).
