## TL;DR
이 장은 이 프로젝트에서 "알고리즘"이라고 부를 만한 로직들을 모았습니다:
(1) 당일 자정마다 1번으로 리셋되는 주문번호 채번, (2) UTC로 저장된
시각을 한국 시간(KST) 기준 하루/한 달 경계로 정확히 잘라내는 날짜
계산, (3) "같은 상품이라도 옵션이 다르면 다른 줄"로 장바구니를
병합하는 복합 키, (4) MongoDB Aggregation Pipeline으로 만드는 월별
매출 통계, (5) 주문 성공과 분리된 재고 차감/알림("fire-and-forget"),
(6) 주문 취소 시 차감했던 재고를 되돌리는 역연산.

## 1. 당일 주문번호 채번 — "스타벅스 매장 주문번호" 알고리즘

```ts
const ordersToday = await Order.countDocuments({
  createdAt: { $gte: getKstStartOfToday() },
});
const newOrder = new Order({ orderNumber: ordersToday + 1, ... });
```

**아이디어**: 오늘 자정(KST) 이후 생성된 주문 개수를 세고, 그 값 +1을
새 주문의 번호로 씁니다. 자정이 지나면 `getKstStartOfToday()`가
가리키는 기준점 자체가 다음 날로 넘어가므로, 카운트가 자동으로
0부터 다시 시작합니다 — 별도의 "매일 자정에 카운터를 리셋하는
배치 작업"이 필요 없습니다.

**동시성에 대한 트레이드오프**: 두 손님이 정확히 같은 순간에 주문을
제출하면, 둘 다 `countDocuments`가 같은 값(예: 5)을 읽어서 둘 다
`orderNumber: 6`이 될 이론적 가능성이 있습니다(read-then-write
사이에 다른 쓰기가 끼어드는 race condition). 완벽하게 막으려면
MongoDB의 원자적 카운터 컬렉션(`findOneAndUpdate`로 `$inc`)을 따로
둬야 하지만, 이 프로젝트는 "화면에 보여주는 짧은 안내 번호"일
뿐이고(`_id`가 진짜 고유 식별자), 실제 매장에서 같은 밀리초에 두
주문이 동시 접수될 확률과 그 피해(번호가 잠깐 겹쳐 보이는 것뿐, 데이터
자체는 안전)를 감안해 단순한 방식을 선택했습니다.

## 2. KST 시간대 날짜 계산 — "오프셋을 더하고 빼는" 트릭

MongoDB/JavaScript의 `Date`는 항상 UTC로 저장/계산됩니다. 하지만
"오늘 하루", "이번 달"의 기준은 사용자에게 익숙한 한국 시간(KST,
UTC+9)이어야 합니다. `apps/backend/src/lib/date.ts`의 핵심 트릭은
**"KST로 보이게 하려고 9시간을 더한 가짜 UTC 시각에서 자정을
계산한 뒤, 다시 9시간을 빼서 진짜 UTC로 되돌린다"**는 것입니다.

```ts
const KST_OFFSET_MS = 9 * 60 * 60 * 1000;

function getKstStartOfToday(): Date {
  const kstNow = new Date(Date.now() + KST_OFFSET_MS); // ①
  kstNow.setUTCHours(0, 0, 0, 0);                       // ②
  return new Date(kstNow.getTime() - KST_OFFSET_MS);    // ③
}
```

- ① 지금 UTC 시각에 9시간을 더합니다. 이러면 이 `Date` 객체의
  "UTC 시/분/초"를 읽었을 때 나오는 값이 **실제로는 한국 시간의
  시/분/초와 같아집니다**(속임수 — 실제 표준시가 바뀐 게 아니라,
  UTC 필드에 KST 값이 우연히 들어가 있는 상태를 만든 것).
- ② `setUTCHours(0,0,0,0)`으로 "그 날짜의 자정"으로 맞춥니다. ①에서
  이미 KST 값이 UTC 필드에 들어가 있으므로, 이 자정은 **KST 기준
  자정**입니다.
- ③ 다시 9시간을 빼서, 그 KST 자정에 해당하는 **진짜 UTC 시각**으로
  되돌립니다. 이 값을 MongoDB 쿼리(`createdAt: { $gte: ... }`)에
  그대로 쓰면, DB에 UTC로 저장된 `createdAt`과 정확히 비교됩니다.

같은 패턴이 `getKstDayRange('2026-09-12')`(하루 범위),
`getKstMonthRange('2026-09')`(한 달 범위)에도 반복됩니다 — 시작점과
"다음 날/다음 달의 시작"(exclusive upper bound)을 한 쌍으로 반환해서,
호출 쪽은 항상 `$gte: start, $lt: end`로 검색하면 됩니다(하루의 끝을
`23:59:59.999`처럼 근사값으로 잡지 않아도 되는 게 장점 — "다음 경계
직전까지"를 정확하게 표현).

**왜 라이브러리(day.js, date-fns-tz 등) 대신 직접 계산했는가**: 이
프로젝트는 시간대가 KST 하나뿐이고 필요한 연산도 "하루/한 달의
시작-끝 구하기" 정도로 한정적입니다. 이 정도 범위에서는 20줄
남짓한 직접 구현이 새 의존성을 추가하는 것보다 간단하다고 판단했습니다.

## 3. 장바구니 병합 키 — "상품 + 옵션 조합"을 하나의 문자열로

```ts
function makeCartItemId(productId, temperature, iceAmount, magicSpell, selectedOptions) {
  const parts = [productId];
  if (temperature) parts.push(`temp:${temperature}`);
  if (iceAmount) parts.push(`ice:${iceAmount}`);
  if (magicSpell) parts.push(`spell:${magicSpell}`);
  if (selectedOptions?.length) parts.push(`opts:${selectedOptions.map(o => o.name).join(',')}`);
  return parts.join(':');
}
```

장바구니에 같은 메뉴를 또 담았을 때 "수량만 +1" 할지 "새 줄을
추가"할지는 **상품 ID뿐 아니라 고른 옵션까지 전부 같아야** 병합해야
맞습니다(예: HOT 아메리카노 1잔 + ICE 아메리카노 1잔은 다른 줄이어야
함). 이걸 매번 여러 필드를 하나하나 비교하는 대신, **옵션 조합을
결정적(deterministic)인 문자열 키 하나로 직렬화**해서
`items.find(item => item.cartItemId === cartItemId)`처럼 단순 비교
한 번으로 끝냅니다. 이 아이디어는 React의 `key` prop처럼 "복합
식별자를 문자열 하나로 만들어 다루기 쉽게 한다"는 흔한 패턴입니다.

주의할 점: `selectedOptions`를 문자열로 합칠 때 **원래 배열의
순서에 의존**합니다(`o.name`을 정렬하지 않고 그대로 join). 지금은
옵션을 고르는 UI가 항상 같은 순서(등록 순서)로 배열을 만들기 때문에
문제가 없지만, 만약 나중에 옵션을 사용자가 자유 순서로 고를 수 있게
바뀐다면 `[...selectedOptions].sort()`로 정렬 후 join하도록 고쳐야
합니다(그렇지 않으면 같은 옵션 조합인데 고른 순서가 달라 다른 줄로
취급되는 버그가 생길 수 있음).

## 4. 월별 매출 통계 — MongoDB Aggregation Pipeline

```ts
await Order.aggregate([
  { $match: { createdAt: { $gte: rangeStart, $lt: rangeEnd } } },
  { $project: {
      month: { $dateToString: { format: '%Y-%m', date: '$createdAt', timezone: '+09:00' } },
      totalPrice: 1,
      totalQuantity: { $sum: '$items.quantity' },
  } },
  { $group: {
      _id: '$month',
      totalRevenue: { $sum: '$totalPrice' },
      totalQuantity: { $sum: '$totalQuantity' },
      orderCount: { $sum: 1 },
  } },
]);
```

**단계별로 무슨 일이 일어나는가**:
1. `$match` — 조회할 연도 범위(1월~12월) 안의 주문만 걸러냅니다(DB가
   전체 주문을 다 스캔하지 않도록 가장 먼저 좁힘).
2. `$project` — 각 주문 문서에 `month`("2026-09" 같은 라벨,
   MongoDB가 **서버 안에서 직접 KST(+09:00)로 변환**해 계산 — 위
   2번 항목의 JS 트릭과 달리, 여기서는 Mongo의 `$dateToString`에
   `timezone` 옵션이 있어 굳이 오프셋을 직접 계산할 필요가
   없습니다)와 그 주문의 총 판매 수량(`items.quantity`들의 합)을
   계산해 붙입니다.
3. `$group` — `month`별로 묶어서 그 달의 총 매출/총 수량/주문 건수를
   더합니다.

**"주문이 없는 달도 0으로 채운다"**: `$group`은 주문이 **있는**
달만 결과에 내놓습니다. 만약 어떤 달에 주문이 0건이면 그 달은
결과 배열에 아예 나타나지 않아서, 프론트엔드 차트의 x축이 뜨문뜨문
끊깁니다. 이를 막으려고 백엔드가 `getMonthLabelsForYear(year)`로
1~12월 라벨 12개를 미리 만들어두고, 집계 결과를 `Map`으로 바꾼 뒤
12개 라벨 각각에 대해 값이 있으면 채우고 없으면 0을 채웁니다:

```ts
const byMonth = new Map(rows.map((r) => [r._id, r]));
const summary = labels.map((month) => {
  const row = byMonth.get(month);
  return { month, totalRevenue: row?.totalRevenue ?? 0, ... };
});
```

**메뉴별 판매 순위**는 비슷하지만 `$unwind`가 하나 더 들어갑니다 —
주문 하나에 메뉴가 여러 개 담겨 있으므로(`items` 배열), `$unwind:
'$items'`로 배열을 낱개 문서처럼 펼친 뒤 `productId`별로 `$group`해서
판매량/매출을 더합니다. 옛날 주문(이미지 URL 필드가 생기기 전에
만들어진 주문)은 `imageUrl`이 비어있을 수 있어서, 그런 경우만 골라
현재 `Product` 컬렉션에서 이미지를 다시 찾아 채우는 폴백도 있습니다
(상품이 삭제됐으면 빈 문자열).

## 5. "응답 먼저, 부가 작업은 그 다음" — Fire-and-Forget 패턴

```ts
await newOrder.save();
res.status(201).json(newOrder);          // ① 응답을 여기서 이미 보냄

try {
  await decrementStockForOrder(req.body.items);   // ② 재고 차감
} catch (stockErr) {
  console.error(...);                             // 실패해도 로그만
}
try {
  await notifyKitchenOfNewOrder(newOrder.orderNumber, newOrder.orderType); // ③ 웹 푸시
} catch (notifyErr) {
  console.error(...);
}
```

주문 저장이 끝나면 **고객에게 성공 응답을 먼저 돌려줍니다**. 그
다음에야 재고 차감과 주방 알림을 시도합니다. 이 순서가 중요한 이유는,
재고 차감이나 웹 푸시 전송 중 하나가 느리거나 실패하더라도(예: R2/
푸시 서비스 장애) **고객의 "주문하기" 버튼 클릭이 실패한 것처럼
보이면 안 되기 때문**입니다 — 주문 자체(핵심 트랜잭션)와 부가
효과(재고, 알림)의 실패 허용 범위가 다르다는 걸 코드 구조로
표현한 것입니다. 재고 차감이 실제로 실패하면 재고 수치가 약간
부정확해질 수 있지만, 그건 다음 주문이나 관리자가 수동으로 바로잡을
수 있는 수준의 문제로 판단했습니다.

같은 이유로 `decrementStockForOrder`와 `notifyKitchenOfNewOrder`는
서로 **완전히 독립된 `try/catch`**로 감쌉니다 — 재고 차감이 실패해도
알림은 정상적으로 시도되어야 하기 때문입니다(하나의 `try` 블록에
같이 넣으면 첫 번째가 던진 예외가 두 번째 코드의 실행 자체를
막아버립니다).

## 6. 재고 차감 — 자동 품절 처리

```ts
export async function decrementStockForOrder(items: OrderItem[]) {
  for (const item of items) {
    const product = await Product.findById(item.productId);
    if (!product || product.stock == null) continue;   // 재고 추적 안 하는 상품은 건너뜀
    const nextStock = Math.max(product.stock - item.quantity, 0);
    product.stock = nextStock;
    if (nextStock <= 0) product.isSoldOut = true;       // 재고 소진 시 자동 품절
    await product.save();
  }
}
```

`Math.max(..., 0)`으로 재고가 음수로 내려가지 않게 막고, 0 이하가
되면 `isSoldOut`을 자동으로 켭니다 — 관리자가 재고를 수동으로
0으로 만들지 않아도 품절 표시가 자동으로 따라옵니다([[재고관리]]
참고). 상품별로 `for...of` 순차 처리를 쓴 이유는 한 주문에 담기는
메뉴 가짓수가 많아야 몇 개 수준이라 병렬화(`Promise.all`)의
이득보다 코드 단순성을 우선한 것입니다.

## 7. 주문 취소 — 재고 차감의 역연산

```ts
export async function restoreStockForOrder(items: StockAdjustableItem[]) {
  for (const item of items) {
    const product = await Product.findById(item.productId);
    if (!product || product.stock == null) continue;
    const nextStock = product.stock + item.quantity;
    product.stock = nextStock;
    if (nextStock > 0) product.isSoldOut = false;   // 재입고와 같은 규칙
    await product.save();
  }
}
```

`decrementStockForOrder`가 `Math.max(..., 0)`으로 하한을 두는 것과
달리, 여기는 상한을 따로 두지 않습니다 — 취소로 되돌리는 수량은
그 주문이 실제로 차감했던 만큼이라 원래 재고를 넘어설 수 없기
때문입니다(차감 후 재고를 조회하는 게 아니라, 취소 시점에 다시
`Product.findById`로 **현재** 재고를 읽어 그 위에 더하므로, 취소 사이에
관리자가 수동으로 재고를 조정했어도 그 값 위에 정확히 더해집니다).

두 함수의 파라미터 타입이 미묘하게 다른 이유도 짚어둘 만합니다.
`decrementStockForOrder`는 주문 생성 요청 바디(`req.body.items`, 아직
저장 전이라 `productId`가 평범한 `string`)를 받고,
`restoreStockForOrder`는 취소 라우트에서 이미 저장된 주문 문서
(`order.items`, Mongoose 서브다큐먼트라 `productId`가 `ObjectId`
인스턴스)를 받습니다. 매번 `String(item.productId)`로 변환하는 대신,
`inventory.ts`에 `{ productId: string | mongoose.Types.ObjectId;
quantity: number }` 형태의 `StockAdjustableItem` 인터페이스를 따로 두고
두 함수 모두 이걸 받게 했습니다 — `Product.findById`는 문자열/ObjectId
둘 다 그대로 받아들이므로 변환 없이 타입만 넓혀 해결한 것입니다.

취소 라우트(`PATCH /api/orders/:id/cancel`)에서도 재고 복원은 주문
취소 자체와 분리된 **별도 `try/catch`**로 감쌉니다 — 취소 처리는 이미
`order.isCancelled = true`로 저장된 뒤이므로, 재고 복원이 실패해도
주문은 정상적으로 취소된 상태를 유지하고 로그만 남습니다. 위 5번의
fire-and-forget과 같은 이유입니다. 다만 순서는 다릅니다 — 주문 생성은
"응답을 먼저 보내고 그 다음에" 부수 효과를 시도하지만, 취소는 이미
동기적으로 `res.json(order)` 이전에 재고 복원을 시도합니다(취소는
관리자가 결과를 보고 다음 행동을 판단해야 하는 화면이라, 응답 자체를
지연시켜도 문제가 없기 때문입니다).

상태 전이 자체의 규칙(진행중 ⇄ 완료, 진행중 → 취소만 가능, 완료된
주문은 취소 불가)은 도메인 정책이라 이 장이 아니라
[[주문상태전이-API]]에 정리했습니다.
