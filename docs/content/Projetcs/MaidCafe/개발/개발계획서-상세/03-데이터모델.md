## TL;DR
컬렉션은 5개뿐입니다(`Product`, `Category`, `Order`, `Ad`,
`PushSubscription`). 관계형 DB의 정규화 본능과 다르게, **"자주 같이
읽히는 데이터는 한 문서에 내장(embed)하고, 시간이 지나도 바뀌면 안
되는 데이터는 스냅샷으로 복사"**하는 MongoDB식 설계를 따릅니다.

## 전체 관계도

```
Category ──(name 문자열로 느슨하게 연결)── Product
                                              │
                                    (주문 시점 스냅샷으로 복사)
                                              ▼
                                          Order.items[]

Ad                       PushSubscription
(독립, 다른 컬렉션과 관계 없음)   (독립, 다른 컬렉션과 관계 없음)
```

`Category`와 `Product`는 MongoDB의 `ObjectId` 참조(`ref`)가 아니라
**카테고리 이름 문자열**로 느슨하게 연결됩니다(`Product.category:
String`). `Order.items`는 주문 당시 상품 정보를 **통째로 복사**해서
저장하고, 이후 원본 `Product`가 바뀌거나 삭제돼도 영향받지 않습니다.

## `Product` — 상품

```ts
{
  name: string;
  price: number;
  imageUrl: string;          // R2 공개 URL
  category: string;          // Category.name과 같은 문자열(참조 아님)
  order: number;              // 같은 카테고리 안에서의 노출 순서
  isSoldOut: boolean;
  stock?: number;             // 없으면(undefined) 재고 추적 안 함
  options: { name: string; price: number }[];  // 메뉴별 자유 옵션(샷 추가 등)
  temperatureOption?: 'BOTH' | 'HOT' | 'ICE';
  hasMagicSpellOption: boolean;
}
```

**설계 근거**
- **`category`가 참조가 아니라 문자열인 이유**: 카테고리는 관리자가
  자유롭게 이름을 바꿀 수 있는 대상입니다([[카테고리관리]]). 만약
  `ObjectId` 참조였다면 카테고리 이름이 바뀔 때 프론트엔드에서 항상
  `Category` 컬렉션과 조인(populate)해야 최신 이름을 보여줄 수
  있는데, 문자열로 저장하면 이름이 바뀌는 순간 그 카테고리에 속한
  모든 상품에 일괄 업데이트가 필요합니다 — 실제로는 카테고리 이름
  변경이 드문 반면 상품 목록 조회는 매우 잦아서, "조회는 조인 없이
  빠르게, 이름 변경 시에만 한 번 갱신"이 더 합리적인 트레이드오프로
  판단했습니다.
- **`stock`이 선택 필드인 이유**: 모든 메뉴가 재고 추적이 필요한 건
  아닙니다(예: 재료가 항상 충분한 메뉴). `stock` 필드 자체가 없으면
  (`undefined`) [[재고관리]] 로직이 그 상품을 건너뜁니다 — "0"과
  "추적 안 함"을 구분하기 위해 boolean 플래그를 따로 두지 않고
  옵셔널 필드 유무 자체를 플래그로 씁니다.
- **`temperatureOption`이 3가지 값인 이유**: `'BOTH'`(HOT/ICE 중
  고객이 선택), `'HOT'`/`'ICE'`(그 온도로 고정 — 카레는 HOT만,
  에이드는 ICE만), 값 없음(온도 옵션 자체가 없는 메뉴). 이렇게
  3+1가지 상태를 하나의 옵셔널 enum으로 표현해 프론트엔드가 이
  값 하나만 보고 UI를 분기합니다([[상품옵션선택]] 참고).
- **`options`(자유 옵션)와 `hasMagicSpellOption`이 서로 다른 방식인
  이유**: `options`는 "이름+추가금" 여러 개를 **동시에 체크박스로
  선택**할 수 있는 목록이라 배열로 저장합니다. "마법의 주문"은
  정해진 목록 중 **하나만 드롭다운으로 고르는** 방식이라, 배열이
  아니라 boolean 토글(이 메뉴에 이 옵션을 노출할지 여부)만 저장하고
  실제 선택지 목록은 프론트엔드 상수(`MAGIC_SPELL_OPTIONS`)로 관리합니다
  — 옵션 목록 자체가 매장 전체에서 고정이기 때문입니다.

## `Category` — 카테고리

```ts
{
  name: string;   // unique
  order: number;  // 노출 순서, 값이 작을수록 앞
}
```

`order`는 배열 인덱스를 그대로 저장하는 방식입니다 — 자세한 재배치
알고리즘은 [[08-관리자-화면-UI-패턴]] 참고.

## `Order` — 주문

```ts
{
  orderNumber: number;        // 당일 자정(KST) 기준 1부터 재채번
  items: {
    productId: ObjectId;      // 참조는 남기지만
    name: string;             // 아래 필드들은 "주문 시점 스냅샷"
    price: number;            // (옵션 추가금이 이미 반영된 최종 단가)
    imageUrl: string;
    quantity: number;
    hasExtraShot?: boolean;   // 레거시 호환용(과거 옵션 구조)
    magicSpell?: string;
    temperature?: 'HOT' | 'ICE';
    iceAmount?: '적게' | '적당' | '많이';
    selectedOptions?: { name: string; price: number }[];
  }[];
  totalPrice: number;
  orderType: 'dine-in' | 'takeout';
  isCompleted: boolean;
  createdAt: Date;
  paymentMethod?: '신용카드' | 'NPay' | 'Kakao Pay' | '토스페이';
}
```

**설계 근거**
- **`items`가 `Product`를 참조(populate)하지 않고 통째로 복사하는
  이유**: 주문은 "그 순간의 사실"에 대한 기록입니다. 나중에 상품
  가격이 오르거나 상품 자체가 삭제돼도, 이미 완료된 과거 주문의
  영수증/통계는 **주문 당시의 가격/이름**으로 남아있어야 합니다.
  `productId`는 참조용으로만 남겨두고(통계 집계에서 조인할 때 씀),
  실제로 화면에 보여줄 값은 전부 스냅샷 필드에서 읽습니다.
- **`orderNumber`가 MongoDB `_id`가 아닌 별도 필드인 이유**: `_id`는
  `507f1f77bcf86cd799439011`처럼 사람이 외치거나 기억하기 불가능한
  값입니다. 카운터 화면(주방)에서 "3번 손님!"처럼 부를 짧은 번호가
  필요해서, 당일 자정 기준으로 1부터 다시 매기는 번호를 별도로
  둡니다(스타벅스 매장 주문번호와 같은 방식). 채번 알고리즘의 동시성
  문제는 [[05-주문-핵심-알고리즘]]에서 다룹니다.
- **`isCompleted`가 상태 enum이 아니라 boolean인 이유**: "주문 상태를
  더 세분화(접수/조리중/준비완료 등)해야 하는가"를 실제로 검토했지만
  ([[주문상태전이-API]]), 이 매장 규모에서는 "진행중/완료" 이분법만
  필요하다고 판단해 boolean으로 충분하다고 결정했습니다. 나중에
  세분화가 필요해지면 그때 enum으로 바꿉니다.

## `Ad` — 광고 배너

```ts
{
  imageUrl: string;
  order: number;      // 노출 순서
  createdAt, updatedAt (timestamps: true)
}
```
가장 단순한 모델입니다 — 이미지와 순서만 있으면 되고, `Product`처럼
복잡한 옵션 구조가 필요 없습니다.

## `PushSubscription` — 웹 푸시 구독

```ts
{
  endpoint: string;   // unique — 브라우저가 발급하는 구독 고유 URL
  keys: { p256dh: string; auth: string };  // 암호화 키 쌍
  createdAt: Date;
}
```
`endpoint`가 `unique`인 이유: 같은 기기/브라우저가 알림을 껐다 다시
켜면 브라우저는 같은(혹은 새) endpoint로 다시 구독을 보내는데,
`endpoint`를 유니크 키로 잡아 upsert하면 중복 구독이 쌓이지 않습니다.
전체 웹 푸시 흐름은 [[07-실시간-알림-아키텍처]] 참고.

## `packages/types` — 프론트/백엔드/모바일이 공유하는 계약

MongoDB 스키마와 API 요청/응답 타입은 완전히 같지 않습니다(예:
`_id`는 있고 없고, 요청 바디엔 `orderNumber`가 없음 등). 그래서
`packages/types/index.ts`에 API 계약 전용 타입을 따로 정의해 세
클라이언트가 전부 이 타입을 import해서 씁니다:

- `Product`, `Category`, `Order`, `OrderItem`, `Ad` — 조회 응답 타입
- `CreateOrderInput` — `POST /api/orders`의 요청 바디
- `OrderListQuery` — `GET /api/orders`의 쿼리 파라미터(`status`,
  `orderType`, `date` 전부 선택)
- `MonthlySalesSummary`, `ProductSalesRanking` — 통계 API 응답
- `AdminLoginInput`, `AdminSessionResponse` — 인증 API 계약
- `UploadImageResponse` — 이미지 업로드 응답

백엔드 라우트 핸들러가 `Request<Params, ResBody, ReqBody, Query>`
제네릭에 이 타입들을 그대로 대입하기 때문에, 요청 바디/쿼리 파라미터
이름이 잘못되면 **컴파일 타임에** 타입 에러가 납니다(런타임에 가서야
발견하는 게 아니라).
