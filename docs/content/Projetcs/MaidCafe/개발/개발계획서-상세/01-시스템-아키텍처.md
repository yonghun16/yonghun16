## TL;DR
이 프로젝트는 **Turborepo 모노레포** 안에 프론트엔드(Next.js), 백엔드
(Express), 모바일 앱(Expo)이 각자 독립 배포되는 **3개의 클라이언트 +
1개의 API 서버** 구조입니다. 프론트엔드/모바일 각각의 내부는
**FSD(Feature-Sliced Design)** 레이어로 나뉘어 있고, 프론트엔드↔백엔드
사이는 서로 다른 오리진(Vercel/Render)이라 **쿠키 문제를 피하려고
Next.js가 백엔드를 프록시**하는 구조입니다.

## 왜 이런 구조를 택했는가

### 1. 왜 모노레포인가
프론트엔드/백엔드/모바일이 `Order`, `Product` 같은 타입을 그대로
공유해야 합니다. 별도 저장소로 쪼개면 이 타입들을 npm 패키지로
퍼블리시하고 버전을 맞추는 오버헤드가 생깁니다. 모노레포 +
`packages/types`를 workspace 의존성으로 참조하면, 백엔드에서 타입을
바꾸는 순간 타입 에러가 프론트엔드/모바일에도 즉시 보여서 계약이
깨지는 걸 컴파일 타임에 잡습니다.

### 2. 왜 백엔드를 Next.js API Route로 합치지 않고 Express로 분리했는가
Next.js API Route로도 REST API를 만들 수 있지만, 이 프로젝트는 처음부터
"클라이언트가 여러 개(웹 + 모바일)"가 될 걸 전제로 설계했습니다. 만약
API를 Next.js 안에 넣으면, 모바일 앱은 Next.js 서버가 배포된 도메인에
직접 HTTP 요청을 날려야 하는데 — 이건 기술적으론 가능하지만 "백엔드가
프론트엔드 프레임워크에 얹혀 있다"는 개념적 결합이 생깁니다. 별도
Express 서버로 분리해두면 프론트엔드가 통째로 바뀌어도(예: Next.js →
다른 프레임워크) 백엔드는 전혀 영향받지 않고, 모바일 앱도 웹과
동등한 자격으로 같은 REST API를 그냥 호출하면 됩니다.

### 3. 왜 FSD(Feature-Sliced Design)인가
이 프로젝트는 **"코드는 AI가 작성하고 사람은 리뷰만 한다"**는 협업
전제가 있습니다(`CLAUDE.md`의 AI/Human 작업 경계 규칙). 사람이 리뷰만
하는 워크플로우에서 가장 중요한 건 "이 코드가 어디 있을지 예측
가능해야 한다"는 것입니다. FSD는 레이어(아래로 갈수록 더
범용적)와 판단 순서("이 코드가 몇 개 앱이 쓰는가 → 도메인 지식이
있는가 → 어떤 종류의 화면 단위인가")가 명확히 정해져 있어서, 새
코드가 생길 때마다 "이건 어디에 둬야 하지?"를 매번 새로 고민하지
않아도 됩니다.

## 모노레포 최상위 구조

```
maid-cafe-kiosk/
├── apps/
│   ├── frontend/    Next.js 15(App Router) — 고객 키오스크 + 관리자 + 주방 화면
│   ├── backend/     Express 5 + MongoDB — REST API 서버
│   └── mobile/      Expo(React Native) — 고객 키오스크 네이티브 앱
├── packages/
│   ├── types/               프론트/백엔드/모바일이 공유하는 계약 타입
│   ├── eslint-config/        공용 ESLint 설정
│   └── typescript-config/    공용 tsconfig
├── docs/            이 문서 포함 — Quartz(Vault) + LeanSpec(스펙) + ADR
└── turbo.json       빌드/테스트 태스크 오케스트레이션(Turborepo)
```

`packages/ui`는 한때 있었지만 아무 데서도 쓰이지 않는 Turborepo 기본
보일러플레이트라 삭제했습니다 — "실제로 2개 이상 앱이 쓰는 게 확인된
것만 `packages/`로 올린다"는 FSD 판단 기준을 인프라 레벨에서도 그대로
지킨 사례입니다.

## 배포 토폴로지

```
                     ┌──────────────────────┐
   고객 태블릿/폰   → │  Vercel (frontend)    │ ← 관리자/주방 PC 브라우저
                     │  Next.js App Router    │
                     └──────────┬─────────────┘
                                │ /api/* 를 그대로 중계(rewrites)
                                ▼
                     ┌──────────────────────┐
                     │  Render (backend)      │ ← 오라클 클라우드가 10분마다
                     │  Express + MongoDB     │    /health 핑(무료 티어 슬립 방지)
                     └──────────┬─────────────┘
                                │
                    ┌───────────┼────────────┐
                    ▼                        ▼
          ┌──────────────────┐   ┌────────────────────┐
          │ MongoDB Atlas     │   │ Cloudflare R2       │
          │ (상품/주문/세션)   │   │ (상품·광고 이미지)   │
          └──────────────────┘   └────────────────────┘

   매장 태블릿(네이티브 앱) → Expo Go(개발) / EAS Build(배포 시)
                             → apps/backend REST API에 직접 요청(프록시 없음)
```

- **프론트엔드(Vercel)**: 고객용 `/`, 관리자용 `/admin`, 주방용
  `/kitchen` 세 화면 모두 이 하나의 Next.js 앱 안에 있습니다.
- **백엔드(Render)**: 무료 티어라 일정 시간 요청이 없으면 슬립 상태로
  들어갑니다. 오라클 클라우드의 무료 인스턴스에서 크론으로 10분마다
  `GET /health`를 호출해 슬립을 방지합니다(자세한 내용은 12장
  [[12-배포-인프라]] 참고).
- **모바일 앱**: 브라우저가 아니라 네이티브 앱이라 CORS 제약이 아예
  적용되지 않습니다. 그래서 프론트엔드처럼 프록시를 거치지 않고
  백엔드 REST API에 직접 요청합니다.
- **이미지**: 상품/광고 이미지는 MongoDB가 아니라 Cloudflare R2(S3
  호환 오브젝트 스토리지)에 저장하고, MongoDB에는 R2 공개 URL만
  문자열로 저장합니다(자세한 파이프라인은 [[06-이미지-파이프라인]]).

## "왜 프론트엔드가 백엔드를 프록시하는가" — 쿠키 문제

프론트엔드(Vercel)와 백엔드(Render)는 **서로 다른 오리진**입니다.
관리자 로그인은 세션 쿠키 기반인데, 브라우저 입장에서 서로 다른
오리진끼리 쿠키를 주고받는 건 "서드파티 쿠키"로 취급됩니다. Safari의
ITP(Intelligent Tracking Prevention)나 크롬의 서드파티 쿠키 단계적
폐지 정책 때문에, 이런 쿠키는 저장이 아예 막히거나 새로고침 후 사라질
수 있습니다.

이걸 근본적으로 피하는 방법은 **브라우저가 항상 같은 오리진에만
요청하게 만드는 것**입니다. `apps/frontend/next.config.js`의
`rewrites()`가 `/api/*` 요청을 프론트엔드 서버가 그대로 받아서
백엔드로 중계(proxy)합니다:

```js
async rewrites() {
  return [{ source: '/api/:path*', destination: `${backendOrigin}/api/:path*` }];
}
```

브라우저는 항상 `내-사이트.vercel.app/api/...`로만 요청을 보내고,
실제로 Render 백엔드로 넘기는 건 Next.js 서버(브라우저가 모르는
서버-서버 통신)가 처리합니다. 그 결과 브라우저 입장에서 쿠키는 항상
퍼스트파티 쿠키가 됩니다.

**주의할 함정**: `rewrites()`의 `destination`에 들어가는
`backendOrigin`은 **빌드 시점**에 한 번 고정됩니다(Next.js의 정적
설정 특성). `next start`를 실행할 때 환경변수를 바꿔도 반영되지
않고, 반드시 `pnpm --filter frontend build` **실행 시점**에 올바른
`BACKEND_ORIGIN`이 설정돼 있어야 합니다. 이 문제로 실제로 로컬
검증 중 "백엔드에 새 라우트를 추가했는데 프론트에서 404(정확히는
Express의 기본 404 HTML)가 난다"는 증상을 겪은 적이 있는데, 원인은
빌드 시점에 이미 다른(배포된) 백엔드 주소로 고정돼버린 것이었습니다.

## 요청이 흘러가는 전체 경로 (예: 고객이 주문 버튼을 누르면)

```
1. 고객 태블릿의 React 컴포넌트(OrderSummary)
   → useCartStore().submitOrder(orderType, paymentMethod) 호출
2. features/cart/api/orderApi.ts
   → axios로 POST /api/orders 요청 (프론트: /api/orders, 모바일: 백엔드 직접 주소)
3. (웹만 해당) Next.js rewrites()가 이 요청을 백엔드 오리진으로 프록시
4. Express: app.ts의 미들웨어 체인
   → cors → express.json() → session(연결된 MongoStore로 세션 조회)
5. routes/orders.ts의 POST / 핸들러
   → getKstStartOfToday()로 "오늘 몇 번째 주문인지" 계산해 orderNumber 채번
   → Order.save()로 MongoDB에 저장
   → 응답을 먼저 반환(201 Created)
   → 그 다음 "fire-and-forget"으로 재고 차감 + 주방 웹 푸시 발송
     (이 두 작업이 실패해도 이미 응답은 나갔으므로 고객 경험에 영향 없음)
6. 프론트엔드: 응답으로 받은 주문 데이터를 lastCompletedOrder에 저장
   → HomePage가 이를 보고 [[주문완료화면]]으로 전환
```

이 흐름에서 **"응답을 먼저 보내고, 부가 작업은 나중에 실패해도
무방하게 분리한다"**는 패턴이 반복해서 나타납니다(재고 차감, 주방
알림 둘 다). 이건 5장([[05-주문-핵심-알고리즘]])에서 더 자세히
다룹니다.
