## TL;DR
"검증된 표준 조합을 고르되, 이 프로젝트의 실제 제약(무료 티어 배포,
AI가 코드 대부분을 작성, 여러 클라이언트가 타입을 공유)에 맞을 때만
예외를 둔다"는 원칙으로 골랐습니다. 아래 표부터 보고, 궁금한 항목의
"왜"만 펼쳐서 읽으면 됩니다.

## 왜 Next.js(App Router)인가
- **서버 컴포넌트 기본**: 상태의 원본이 항상 서버라는 원칙(이
  프로젝트의 상태 관리 규칙)과 잘 맞습니다 — 데이터 조회는 가능한
  서버에서, 상호작용이 필요한 부분만 클라이언트 컴포넌트로 좁힙니다.
- **파일 기반 라우팅**: `/`, `/admin`, `/kitchen` 세 화면을 별도
  라우터 설정 없이 폴더 구조만으로 나눌 수 있습니다.
- **PWA 대응이 쉬움**: `app/manifest.ts`, `app/icon.png` 같은 파일
  컨벤션만으로 PWA 매니페스트/아이콘이 자동 생성됩니다
  ([[PWA설치]] 참고).
- **`rewrites()`가 내장돼 있음**: 1장([[01-시스템-아키텍처]])에서
  설명한 프록시(쿠키 문제 해결)를 별도 서버 없이 프레임워크 기능만으로
  구현할 수 있습니다.

## 왜 Zustand인가 (Redux Toolkit 대신)
- **보일러플레이트가 거의 없음**: `create((set, get) => ({...}))` 하나로
  스토어가 끝납니다. Redux Toolkit은 slice/reducer/selector 구조가
  필요해서, 이 프로젝트처럼 스토어 대부분이 "이 화면 하나만 쓰는 로컬
  전역 상태"(장바구니, 카테고리 필터 등)인 경우엔 과합니다.
- **Provider가 필요 없음**: Context API 기반 상태관리와 달리 컴포넌트
  트리를 Provider로 감쌀 필요가 없어, `app/layout.tsx`가 라우팅
  조립에만 집중할 수 있습니다.
- **선택적 구독**: `useCartStore((state) => state.totalPrice)`처럼
  스토어의 일부 필드만 구독할 수 있어, 관련 없는 상태가 바뀌어도
  불필요한 리렌더가 일어나지 않습니다.

## 왜 Tailwind CSS인가
- 클래스명을 따로 짓지 않아도 됩니다(CSS Modules/styled-components는
  매번 `.module.css` 파일이나 컴포넌트별 스타일 정의가 필요).
- 이 프로젝트는 반응형 분기(`md:`, `lg:`)가 화면 대부분에 있는데(고객
  화면이 폰/태블�it/데스크탑을 전부 지원), Tailwind의 반응형
  프리픽스 문법이 이런 요구와 정확히 맞습니다.
- **모바일 앱과 문법을 공유**: NativeWind가 Tailwind 문법을 그대로
  React Native에 가져오기 때문에, 웹에서 익힌 `flex-row`, `gap-2`
  같은 클래스를 모바일에서도 거의 그대로 씁니다(다만 `grid`, `hover:`
  등 웹 전용 유틸리티는 RN에서 동작하지 않아 포팅 시마다 확인
  필요 — [[10-모바일-앱-아키텍처]] 참고).

## 왜 Express인가 (Fastify/NestJS 대신)
- **가장 단순한 선택지**: 이 백엔드는 REST 엔드포인트 7개 라우터
  (`admin`, `uploads`, `categories`, `products`, `ads`, `orders`,
  `push`)로 구성된 비교적 작은 API 서버입니다. NestJS의
  모듈/데코레이터/DI 컨테이너는 이 규모에는 과합니다.
- **미들웨어 생태계**: `express-session`, `connect-mongo`, `cors`,
  `multer`처럼 필요한 기능이 전부 검증된 Express 미들웨어로
  존재합니다.
- **Express 5**: Express 4가 아니라 5를 쓴 이유는 5부터 async 라우트
  핸들러 안에서 발생한 에러를 별도 `try/catch` 없이도 자동으로
  에러 핸들링 미들웨어로 넘겨주기 때문입니다(다만 이 프로젝트
  코드는 명시적으로 `try/catch`를 쓰는 스타일을 유지합니다 — 에러
  메시지를 상황별로 다르게 주기 위해서입니다).

## 왜 MongoDB + Mongoose인가 (PostgreSQL 대신)
- **스키마가 자주 진화함**: 상품의 `options`(메뉴별 자유 옵션),
  `temperatureOption`, `hasMagicSpellOption`처럼 기능이 늘어날 때마다
  선택적 필드가 추가돼 왔습니다. 관계형 DB였다면 매번 마이그레이션이
  필요했을 변경들이, MongoDB에서는 스키마에 필드만 추가하면 기존
  문서는 그 필드가 없는 채로("옵션 필드는 없으면 undefined") 계속
  유효합니다.
- **주문 아이템의 스냅샷 저장과 잘 맞음**: 주문(`Order.items`)은
  주문 시점의 상품 이름/가격/옵션을 그대로 복사해서 저장합니다(나중에
  상품 가격이 바뀌거나 삭제돼도 과거 주문 기록은 그대로 유지돼야
  하기 때문). 이런 "그 시점의 스냅샷을 통째로 문서 하나에 내장"하는
  패턴은 관계형 테이블 조인보다 document DB의 중첩 구조가 자연스럽게
  표현합니다.
- 실제 데이터 모델과 각 필드의 설계 근거는 [[03-데이터모델]] 참고.

## 왜 Cloudflare R2인가 (AWS S3 대신)
- **이그레스(egress) 비용이 없음**: R2는 아웃바운드 트래픽 요금이
  없어서, 상품 이미지를 고객이 계속 조회해도 대역폭 비용이 들지
  않습니다 — 포트폴리오/소규모 매장 운영에 적합한 비용 구조입니다.
- **S3 호환 API**: `@aws-sdk/client-s3`를 그대로 쓸 수 있어서, AWS
  SDK 생태계(타입, 예제)를 그대로 재사용하면서 엔드포인트만 R2로
  바꾸면 됩니다(`region: 'auto'`로 리전 개념 자체를 생략).

## 왜 Web Push인가 (WebSocket 대신)
백엔드가 Render **무료 티어**라는 제약이 결정적이었습니다. 무료
티어는 일정 시간 요청이 없으면 슬립하고, 외부에서 주기적으로
`/health`를 핑해서 슬립을 막는 구조입니다(1장 참고). WebSocket처럼
"연결을 계속 유지해야 하는" 방식은 이 슬립/헬스체크 구조와 상성이
나쁩니다 — 반면 Web Push는 **알림을 보낼 그 순간에만** 백엔드가
살아있으면 되고(주문이 들어온 순간은 어차피 API 요청이 오는
순간이라 서버가 깨어있음이 보장됨), 평소에는 어떤 연결도 유지할
필요가 없습니다. 자세한 구조는 [[07-실시간-알림-아키텍처]] 참고.

## 왜 Expo인가 (React Native CLI 직접 설정 대신)
- 네이티브 빌드 설정(Android Gradle, iOS Xcode 프로젝트)을 직접
  안 만져도 개발을 시작할 수 있습니다(`Expo Go` 앱으로 즉시 실행).
- 아이콘/스플래시 생성, OTA 업데이트, 추후 `expo-dev-client`로의
  전환까지 하나의 생태계 안에서 점진적으로 확장할 수 있습니다.
- 다만 안드로이드 Lock Task Mode(키오스크 완전 잠금) 같은 커스텀
  네이티브 모듈이 필요한 기능은 Expo Go로는 불가능합니다 — 이
  트레이드오프와 실제 결정은
  `docs/decisions/0001-kiosk-lock-screen-pinning.md` 참고.

## 왜 Turborepo인가
- `turbo run build`처럼 태스크 하나를 실행하면, 의존하는 패키지(예:
  `packages/types`)가 먼저 빌드되고 그 다음 이를 참조하는 앱이
  빌드되는 순서를 자동으로 계산합니다.
- 캐싱: 코드가 안 바뀐 태스크는 재실행하지 않고 이전 결과를 그대로
  씁니다(로컬/CI 모두).
- `turbo.json`에 태스크(`build`, `dev`, `check-types`, `lint`,
  `test`)를 한 번만 정의해두면, 새 앱을 추가해도 그 앱의
  `package.json`에 같은 이름의 스크립트만 정의하면 자동으로
  오케스트레이션에 편입됩니다.
