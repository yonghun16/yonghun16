## TL;DR
주방 화면(`/kitchen`)이 브라우저 탭을 안 보고 있어도, 새 주문이
들어오면 OS 알림(데스크탑 알림 센터/안드로이드 알림바)이 뜹니다.
WebSocket 같은 상시 연결 없이, **VAPID 키 기반 Web Push**로
"알림을 보낼 때만" 서버가 잠깐 관여하는 구조입니다. Render 무료
티어(상시 연결 유지가 어려움)라는 인프라 제약이 이 설계를 결정했습니다
(자세한 배경은 [[02-기술스택과-선정이유]]).

## 왜 WebSocket이 아니라 Web Push인가
WebSocket은 클라이언트-서버가 **연결을 계속 열어둬야** 합니다.
Render 무료 티어는 일정 시간 요청이 없으면 슬립하고, 이 프로젝트는
슬립 방지를 "10분마다 외부에서 `/health`를 핑"하는 방식으로
해결합니다(1장 참고) — 이건 "가끔 짧은 HTTP 요청이 오는" 패턴이지
"연결을 계속 유지하는" 패턴이 아닙니다. Web Push는 **알림을 보내는
그 순간에만** 백엔드 프로세스가 살아있으면 되고(마침 그 순간은
`POST /api/orders` 요청이 막 들어와서 서버가 이미 깨어있는
순간이기도 함), 평소에는 어떤 연결도 유지할 필요가 없어 이
인프라와 훨씬 잘 맞습니다.

## 전체 구조

```
[구독(켜기) 흐름]
주방 화면(브라우저)
  1. Notification.requestPermission() → 사용자가 허용
  2. GET /api/push/vapid-public-key    → 공개키 받기
  3. registration.pushManager.subscribe({ applicationServerKey })
     → 브라우저가 자체적으로 endpoint(구독 고유 URL) + 암호화 키(p256dh, auth) 발급
  4. POST /api/push/subscribe          → { endpoint, keys }를 DB에 저장

[알림 발송 흐름]
POST /api/orders (새 주문)
  → 응답을 먼저 보낸 뒤(5장의 fire-and-forget)
  → notifyKitchenOfNewOrder(orderNumber, orderType)
     → PushSubscription.find() 로 저장된 구독 전부 조회
     → 구독마다 webpush.sendNotification(endpoint+keys, payload)
        (실제로는 브라우저 벤더의 푸시 서비스, 예: Google FCM/Mozilla 서버가 중계)
  → 각 브라우저의 서비스워커가 'push' 이벤트를 받아 self.registration.showNotification() 호출
  → 사용자가 알림을 클릭하면 'notificationclick' 이벤트로 /kitchen 탭에 포커스(없으면 새로 염)
```

## VAPID란 무엇이고 왜 필요한가
Web Push 표준은 "누가 이 구독에 알림을 보낼 자격이 있는지"를 증명할
방법이 필요합니다(그렇지 않으면 아무나 브라우저의 구독 endpoint만
알면 알림을 스팸으로 보낼 수 있음). VAPID(Voluntary Application
Server Identification)는 서버가 **공개키/개인키 한 쌍**을 갖고,
개인키로 서명한 토큰을 매 발송마다 실어 보내서 "이 알림은 정말 이
서버가 보낸 것"임을 브라우저의 푸시 서비스(FCM 등)가 검증하게
합니다.

```ts
const isConfigured = Boolean(VAPID_PUBLIC_KEY && VAPID_PRIVATE_KEY);
if (isConfigured) {
  webpush.setVapidDetails(VAPID_SUBJECT, VAPID_PUBLIC_KEY, VAPID_PRIVATE_KEY);
}
```

- **공개키**는 브라우저에도 필요합니다(`pushManager.subscribe()`의
  `applicationServerKey`) — 그래서 `GET /api/push/vapid-public-key`가
  인증 없이 공개돼 있습니다(공개키는 이름 그대로 공개해도 안전).
- **개인키**는 서버만 갖고, 절대 클라이언트에 노출되면 안 됩니다.
- **`VAPID_SUBJECT`**는 `mailto:` 형식의 연락처입니다 — 푸시 서비스가
  문제가 생겼을 때(예: 남용 신고) 연락할 곳을 요구하는 표준 규격이라,
  실제 운영자 개인 이메일 대신 플레이스홀더(`mailto:admin@example.com`)를
  써도 기능상 문제없습니다.

## `applicationServerKey`는 왜 Base64 문자열을 `Uint8Array`로 바꿔야 하는가
서버가 주는 VAPID 공개키는 사람이 다루기 편한 URL-safe Base64
문자열입니다. 하지만 브라우저의 `PushManager.subscribe()` API는
`BufferSource`(바이트 배열)만 받습니다. `urlBase64ToUint8Array`
헬퍼가 이 변환을 담당합니다 — Web Push 관련 튜토리얼/라이브러리에
거의 항상 등장하는 정형화된 변환 코드입니다(URL-safe 문자
치환(`-`→`+`, `_`→`/`) 후 `atob`로 디코드, 문자 코드 배열로 변환).

## 구독의 생명주기 — 상태의 원본은 항상 브라우저

```ts
const existing = await registration.pushManager.getSubscription();
setStatus(existing ? 'on' : 'off');
```

프론트엔드는 "알림이 켜져 있는지"를 별도 상태(localStorage 등)로
저장하지 않고, **매번 브라우저에게 직접 물어봅니다**
(`pushManager.getSubscription()`). 이렇게 하는 이유는 구독이
"브라우저(정확히는 origin) 단위로 독립적"이기 때문입니다 — 로컬
개발 주소(`localhost:3000`)에서 켠 알림과 배포 주소에서 켠 알림은
서로 다른 구독입니다. 별도 상태를 저장했다면 "새로고침하면 알림이
꺼져 보인다"처럼 브라우저의 실제 상태와 앱이 기억하는 상태가
어긋나는 문제가 생길 수 있는데, 브라우저 API를 그대로 상태의 원본
(source of truth)으로 삼으면 이런 불일치가 애초에 발생하지 않습니다.

## 만료된 구독 자동 정리

```ts
try {
  await webpush.sendNotification({ endpoint, keys }, payload);
} catch (err) {
  const statusCode = err.statusCode;
  if (statusCode === 404 || statusCode === 410) {
    await PushSubscription.deleteOne({ endpoint });   // 만료된 구독은 DB에서 제거
  } else {
    console.error(...);   // 다른 종류의 에러는 로그만 남기고 구독은 유지
  }
}
```

브라우저 구독은 영구적이지 않습니다 — 사용자가 알림 권한을
취소하거나, 브라우저 데이터를 지우거나, 일정 기간 뒤 푸시 서비스가
자체적으로 만료시킬 수 있습니다. 이때 그 구독으로 알림을 보내면
푸시 서비스가 404/410을 응답합니다. 이 상태 코드를 받으면 그
구독을 DB에서 지워서, 다음 발송부터는 죽은 구독에 매번 요청을
보내는 낭비를 막습니다. 구독 여러 개를 `Promise.all`로 동시에
처리하면서, 하나가 실패해도 (`try/catch`를 반복문 안에 둬서) 다른
구독 발송에는 영향이 없게 합니다.

## 서비스워커의 두 이벤트 리스너

```ts
self.addEventListener('push', (event) => {
  const { title, body, url } = event.data.json();
  event.waitUntil(self.registration.showNotification(title, { body, icon: '/icon.png', data: { url } }));
});

self.addEventListener('notificationclick', (event) => {
  event.notification.close();
  const targetUrl = event.notification.data?.url ?? '/kitchen';
  event.waitUntil((async () => {
    const allClients = await self.clients.matchAll({ type: 'window', includeUncontrolled: true });
    const existing = allClients.find((client) => client.url.includes(targetUrl));
    if (existing) await existing.focus();
    else await self.clients.openWindow(targetUrl);
  })());
});
```

- **`push`**: 서버가 보낸 알림 데이터를 실제 OS 알림으로 띄웁니다.
  `event.waitUntil()`로 감싸는 이유는, 이 비동기 작업이 끝나기
  전에 브라우저가 서비스워커를 재우면 알림이 표시되지 않을 수
  있기 때문입니다(서비스워커에게 "이 작업 끝날 때까지 살려달라"고
  알리는 표준 방법).
- **`notificationclick`**: 이미 `/kitchen` 탭이 열려 있으면 새로
  열지 않고 그 탭에 포커스만 옮깁니다(탭이 여러 개 쌓이는 것을
  방지) — `clients.matchAll()`로 현재 열린 모든 창을 확인 후
  URL이 일치하는 게 있는지 찾습니다.

## 발견 당시 아무 효과가 없었던 실수 — 서비스워커 미등록
`@serwist/next`로 서비스워커 코드(`sw.ts`) 자체는 이미 프로젝트에
있었지만, 실제로 브라우저에 **등록하는 코드가 빠져 있어서** 이
기능을 붙이기 전까지 전혀 동작하지 않고 있었습니다.
`@serwist/next/react`의 `<SerwistProvider swUrl="/sw.js">`를
`app/layout.tsx`에 추가해야 브라우저가 실제로
`navigator.serviceWorker.register()`를 호출합니다 — 서비스워커
빌드 산출물이 존재하는 것과, 그게 실제로 등록되어 동작하는 것은
별개라는 걸 보여준 사례입니다.

## 실기기 검증에서 드러난 함정들
실제 배포(Render + Vercel) 환경에서 여러 기기로 테스트한 결과:

- **안드로이드 Chrome**: 정상 동작.
- **안드로이드 삼성 인터넷**: 알림이 오지 않음 — 이 브라우저의
  배터리 최적화가 백그라운드 푸시 전달을 막는 경우가 많다고 알려져
  있어, 구현 버그가 아니라 브라우저 자체의 한계로 판단했습니다.
- **데스크탑 Chrome/Brave**: "알림 켜기"를 눌러도 에러 없이 아무
  반응이 없었던 문제 — 원인은 **macOS 시스템 설정 → 알림에서 해당
  브라우저 앱 자체의 알림이 꺼져 있던 것**이었습니다. 브라우저 안의
  `Notification.requestPermission()`이 `'granted'`를 반환해도, OS
  레벨에서 그 앱의 알림 표시 자체를 막아두면 알림이 뜨지 않습니다 —
  브라우저 권한과 OS 권한은 별개의 레이어라는 걸 실제로 겪은 사례.
- 이 과정에서 실제 버그 2개를 함께 발견해 고쳤습니다: VAPID 두 키
  중 하나만 빠져도 에러 없이 조용히 알림이 전송되지 않던 문제
  (서버 시작 로그에 어느 키가 빠졌는지 명시하도록 보강), 구독 상태
  확인 로직에 에러 처리가 없어 실패해도 조용히 "꺼짐"으로만 보이던
  문제(`try/catch` + origin/구독 존재 여부 로깅 추가).
