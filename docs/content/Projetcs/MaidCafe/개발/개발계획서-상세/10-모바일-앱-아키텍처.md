## TL;DR
`apps/mobile`은 웹(`apps/frontend`)과 **같은 FSD 레이어 구조를 그대로
복사**하지만, 비즈니스 로직은 패키지로 공유하지 않고 **각자 독립적으로
다시 구현**합니다(의도적 결정). 이 장의 핵심은 이 프로젝트에서 두 번
반복해서 겪은 교훈입니다 — **"크기(글자/패딩)는 반응형 className으로
안전하지만, 구조(방향 전환/보임·숨김 전환)를 반응형 className으로
바꾸는 건 이 RN 환경에서 신뢰할 수 없다"**는 것입니다.

## 왜 웹 로직을 `packages/`로 공유하지 않았는가
"장바구니 로직처럼 웹과 모바일에 똑같이 필요한 코드는 공유 패키지로
빼는 게 당연히 낫지 않은가?"라는 질문에 대한 답입니다. 이 프로젝트는
**의도적으로 복붙 후 각자 조정**하는 방식을 택했습니다:
- 웹은 브라우저 DOM API(`window`, `IntersectionObserver`)를 쓰고,
  모바일은 RN API(`useWindowDimensions`, 제스처 리스폰더)를 씁니다 —
  같은 요구사항이라도 구현 자체가 플랫폼마다 다릅니다.
- 지금 시점에 억지로 공유 가능한 형태로 추상화하면, 그 추상화 계층
  자체가 두 플랫폼의 차이를 억지로 가리는 복잡도를 만듭니다.
- "두 구현이 갈라지기 시작하면 그때 공유를 재검토한다"는 원칙을
  세웠습니다 — 아직은 각 구현이 100줄 안팎의 작은 스토어들이라,
  중복의 비용보다 조기 추상화의 비용이 더 크다고 판단했습니다.

## FSD 레이어가 그대로 대응됨

```
apps/frontend/src/          apps/mobile/src/
├── views/home              ├── views/home
├── widgets/product-list     ├── widgets/product-list
├── widgets/order-summary     ├── widgets/order-summary
├── widgets/order-type-select  ├── widgets/order-type-select
├── widgets/order-complete       ├── widgets/order-complete
├── entities/product           ├── entities/product
├── entities/category            ├── entities/category
├── entities/ad                    ├── entities/ad
├── features/cart                    ├── features/cart
├── features/order-type                ├── features/order-type
└── shared/{ui,api,config,lib}           └── shared/{ui,api,config,lib}
```

모바일은 고객용 화면만 있어서(관리자/주방 화면은 웹 전용) 웹보다
슬라이스 개수가 적습니다. `add-product-form`, `manage-*`,
`sales-dashboard` 같은 관리자 전용 위젯은 모바일에 아예 없습니다.

## NativeWind — Tailwind 문법을 그대로 RN에

```js
// apps/mobile/tailwind.config.js
module.exports = { presets: [require('nativewind/preset')], content: [...] };
```

웹에서 `<div className="flex-row items-center gap-2 md:gap-4">`라고
쓰던 감각을 `<View className="flex-row items-center gap-2
md:gap-4">`로 거의 그대로 옮길 수 있습니다. 다만 `grid`, `hover:`처럼
브라우저 전용 개념은 RN에 대응 개념이 없어 동작하지 않으므로, 포팅할
때마다 클래스를 그대로 복붙하지 않고 검증이 필요합니다.

## 태블릿 대응 — 왜 두 가지 다른 방식을 함께 쓰는가

이 프로젝트는 폰(Pixel)과 태블릿(Galaxy Tab, dp 폭 약 927 — Tailwind
`md`~`lg` 구간) 양쪽에서 써야 합니다. **크기 조정**은 `md:text-2xl`
처럼 NativeWind의 반응형 className으로 문제없이 동작했지만, **레이아웃
구조 자체를 바꾸는** 시도는 두 번 다 실패했습니다.

### 실패 사례 1 — `AdBanner`의 `w-full` + `aspectRatio`
광고 배너를 4:3 비율로 만들 때 `className="w-full aspect-[4/3]"`
(퍼센트 너비 + 종횡비 클래스 조합)을 썼더니, 실기기에서 실제 렌더링
비율이 4:3이 아니라 거의 정사각형에 가깝게(`uiautomator dump`로 실측한
bounds 비율 0.899) 잘못 렌더링됐습니다 — 이 RN/Yoga 레이아웃 엔진
환경에서 **퍼센트 너비와 `aspectRatio`를 함께 쓰는 조합** 자체가
문제였습니다(고정 px 너비 + `aspectRatio` 조합은 정상 동작하는 것으로
별도 확인). 해결책은 `onLayout`으로 부모의 실제 가용 너비를 실측한 뒤,
`useWindowDimensions`로 판단한 태블릿/폰 여부에 따라 최대 너비를
고르고, **JS에서 직접 계산한 `width`/`height` px 값**을 `style`로
줍니다 — className의 반응형 유틸이 아니라 명시적 숫자로 Yoga에게
정확한 치수를 알려주는 방식입니다.

### 실패 사례 2 — 태블릿 좌우 분할 레이아웃
웹의 `md:flex-row`(태블릿 이상에서 메뉴 목록 + 장바구니를 좌우로
나눔)를 RN에도 똑같이 `className="flex-1 md:flex-row"` +
`md:w-3/5`/`md:w-2/5` + `hidden`/`md:flex` 조합으로 그대로 옮겼습니다.
`check-types`는 통과했지만, 실제 태블릿 화면을 스크린샷/`uiautomator
dump`로 확인해보니 장바구니 사이드바와 카테고리 탭이 같은 자리에
겹쳐서 화면이 완전히 깨져 있었습니다. `check-types`가 이런 **런타임
레이아웃 버그**는 전혀 잡아내지 못한다는 걸 보여준 사례입니다.

### 정착한 규칙 — "크기는 className, 구조는 JS 분기"

```ts
const TABLET_BREAKPOINT = 768;   // Tailwind md
const { width } = useWindowDimensions();
const isTablet = width >= TABLET_BREAKPOINT;

<View className={isTablet ? 'flex-1 flex-row' : 'flex-1'}>
  <ProductList />   {/* 내부에서 style={isTablet ? { width: '60%' } : undefined} */}
  <OrderSummary />  {/* isTablet 여부로 사이드바 vs 하단 바를 아예 다른 JSX로 분기 */}
</View>
```

`OrderSummary`는 `hidden md:flex`처럼 **두 버전을 동시에 마운트하고
CSS로 숨기는 방식** 대신, `{isTablet ? <사이드바 JSX> : <하단 바
JSX>}`로 **애초에 하나만 마운트**합니다 — 실패 사례 2의 근본
원인(반응형 구조 전환 자체가 이 환경에서 불안정)을 완전히 우회하는
가장 확실한 방법이기 때문입니다.

**교훈을 일반화하면**: 이 RN 버전/아키텍처에서 `md:` 같은 반응형
프리픽스는 "이미 정해진 스타일 값 중 하나를 고르는" 용도(글자 크기,
패딩, 색상)로는 안정적이지만, "레이아웃의 근본 구조(방향, 보임/숨김,
비율)를 조건부로 바꾸는" 용도로는 신뢰할 수 없었습니다. 후자가
필요하면 항상 `useWindowDimensions()` 값을 JS 조건문으로 직접
분기합니다.

## 세션 타임아웃 — 별도 네이티브 화면(Modal)을 넘나드는 감지

웹은 `window.addEventListener('pointerdown', ...)`처럼 문서 전체에
이벤트를 걸면 모달 안 클릭도 자연히 잡힙니다(모달이 같은 DOM 트리
안에 있으므로). RN의 `<Modal>`은 iOS `UIViewController`/안드로이드
`Dialog`라는 **완전히 별도의 네이티브 화면**으로 뜹니다. 최상위
화면에만 감지기를 달면 옵션 선택/결제 모달 안에서의 조작을 놓칩니다.

**시도했다가 실패한 방법**: 웹의 `onTouchStartCapture`와 이름이
비슷해서 처음 시도했지만, 이 RN 타입 정의에는 `View`에도 없어
컴파일 에러가 났습니다.

**실제로 쓴 방법 — `onStartShouldSetResponderCapture`**: RN의
제스처 리스폰더 시스템이 "이 뷰가 터치의 응답자가 되고 싶은가?"를
루트에서부터 각 조상에게 묻는(캡처 단계) 콜백입니다. 항상 `false`를
반환해 실제 터치 처리(버튼 `onPress` 등)는 그대로 자식에게 넘기고,
**콜백 자체가 모든 터치 시작 시점에 호출된다는 사실만** 부수효과로
이용해 타이머를 갱신합니다:

```ts
<View onStartShouldSetResponderCapture={() => { resetIdleTimer(); return false; }}>
```

이 핸들러를 `HomePage`의 화면 루트 `View`와
`shared/ui/Modal.tsx`의 모달 오버레이 `View` **양쪽에** 달아서,
메인 화면 조작과 모달 안 조작 둘 다 감지합니다. 타이머 로직 자체는
`shared/lib/idleTimer.ts`에 **모듈 전역 함수**(React state나
Zustand가 아님)로 뒀는데, 이유는 `shared/ui/Modal`이 FSD 규칙상
`features/`를 import할 수 없어서 — `HomePage`와 `Modal`이 같은
타이머를 공유하려면 그 로직 자체가 두 곳 모두 접근 가능한
`shared/`에 있어야 했기 때문입니다.

**검증 중 얻은 메타 교훈**: 타임아웃을 6초로 줄여 테스트하다가
"모달 안 터치가 감지 안 된다"고 잘못 판단한 적이 있는데, 실제
원인은 메커니즘이 아니라 **스크린샷을 읽고 다음 명령을 입력하는
사이의 실제 경과 시간**이 6초를 넘겨버린 테스트 방법의 문제였습니다.
탭-대기-탭을 전부 하나의 셸 명령으로 묶어 중간에 개입할 틈을 없애고
나서야 정상 동작을 확인했습니다 — 시간 민감한 로직을 실기기에서
검증할 때는 "검증 자체가 걸리는 시간"도 계산에 넣어야 한다는
교훈입니다.

## 카테고리 탭 — 한 줄 고정 + 드래그/버튼 스크롤

폰 폭에서 카테고리가 5개면 줄바꿈되어 헤더가 두꺼워지는 문제를,
`flex-row flex-wrap` 대신 `horizontal ScrollView`로 바꿔 해결했습니다
(웹의 헤더 도킹 카테고리 바가 `variant="scroll"`로 같은 문제를 푸는
것과 동일한 발상). 이 과정에서 겪은 작은 버그: `ScrollView`의
`contentContainerStyle`에 `alignItems`를 지정하지 않으면 기본값
`stretch` 때문에 버튼들이 컨테이너 세로 높이만큼 늘어나 보였습니다
(`alignItems: 'center'`로 해결). 좌우 화살표 버튼은 스크롤 위치를
`categoryScrollOffsetRef`(리렌더를 피하려고 state가 아니라 ref)에
기록해뒀다가, 버튼을 누르면 그 값 기준으로 `scrollTo({ x, animated:
true })`를 호출합니다.

## 안드로이드 태블릿 잠금은 왜 이 장에 없는가
"매장 태블릿을 다른 화면으로 못 나가게 잠근다"는 기능은 앱 코드가
아니라 **운영 절차(Screen Pinning)**로 해결하기로 결정했습니다 —
Expo와 호환되는 신뢰할 만한 라이브러리가 없었고, 이 프로젝트
규모(매장 하나)에는 Device Owner 완전 잠금까지 필요하지 않다고
판단했기 때문입니다. 자세한 배경과 iOS(Guided Access) 비교는
`docs/decisions/0001-kiosk-lock-screen-pinning.md` 참고.
