## TL;DR
계정별 로그인이 아니라 **공유 비밀번호 하나 + 서버 세션**입니다.
비밀번호 비교는 타이밍 공격을 막는 `timingSafeEqual`을 쓰고, 세션은
MongoDB에 저장(`connect-mongo`)해서 서버가 재시작돼도 로그인이
풀리지 않습니다. 프론트엔드(Vercel)와 백엔드(Render)가 다른
오리진이라 쿠키가 새는/막히는 문제가 있었는데, 프록시(1장)와
`trust proxy` 설정으로 해결했습니다.

## 왜 계정별 로그인이 아니라 공유 비밀번호인가
매장 하나, 관리자/직원 소수라는 규모를 감안한 의도적 결정입니다.
점주/직원 역할을 나누거나 조작 이력(감사 로그)을 남기는 건 매장이
여러 개거나 직원 수가 많을 때 필요한데, 이 프로젝트 규모에는 실익이
없다고 판단해 하지 않기로 확정했습니다 — 결제 게이트웨이 연동을
범위 밖으로 정한 것과 같은 종류의 스케일 판단입니다(자세한 내용은
[[관리자인증인가]] 참고).

## 로그인 흐름

```
POST /api/admin/login { password }
  → process.env.ADMIN_PASSWORD와 비교
  → 일치하면 req.session.isAdmin = true
  → 세션이 MongoDB(connect-mongo)에 저장되고, 서명된 세션 ID가
    httpOnly 쿠키로 브라우저에 내려감
```

이후 관리자 전용 API는 `requireAdmin` 미들웨어가 `req.session.isAdmin`
값만 확인합니다:

```ts
export function requireAdmin(req, res, next) {
  if (!req.session.isAdmin) {
    res.status(401).json({ message: '관리자 인증이 필요합니다.' });
    return;
  }
  next();
}
```

## 왜 비밀번호를 `===`로 비교하지 않는가 — 타이밍 공격

```ts
const isValid =
  typeof password === 'string' &&
  password.length === adminPassword.length &&
  timingSafeEqual(Buffer.from(password), Buffer.from(adminPassword));
```

JavaScript의 `===` 문자열 비교는 **앞에서부터 한 글자씩 비교하다가
다른 글자가 나오는 순간 즉시 false를 반환**합니다. 이 말은 정답과
"앞 3글자만 맞는 시도"가 "앞 1글자만 맞는 시도"보다 아주 미세하게
더 오래 걸린다는 뜻입니다. 공격자가 응답 시간을 수천~수만 번 측정해
평균을 내면, 이 미세한 시간 차이로 한 글자씩 맞춰나갈 수 있습니다
(타이밍 공격). `timingSafeEqual`은 문자열 길이가 같으면 **항상
동일한 시간**이 걸리도록 모든 바이트를 끝까지 비교합니다(중간에
다른 게 나와도 멈추지 않음).

`password.length === adminPassword.length`를 먼저 체크하는 이유는
`timingSafeEqual` 자체가 **길이가 다른 두 버퍼를 넘기면 예외를
던지기** 때문입니다 — 길이 체크는 타이밍에 영향을 주지만("긴
비밀번호 시도가 짧은 것보다 오래 걸리는지"로 길이를 유추당할 여지가
이론적으로 남음), 실용적으로는 충분한 방어 수준으로 판단했습니다.

## 세션을 어디에 저장하는가 — `connect-mongo`

```ts
app.use(session({
  secret: SESSION_SECRET,
  store: MongoStore.create({ mongoUrl: sessionMongoUrl }),
  cookie: {
    httpOnly: true,
    secure: process.env.NODE_ENV === 'production',
    sameSite: process.env.NODE_ENV === 'production' ? 'none' : 'lax',
    maxAge: 1000 * 60 * 60 * 8,  // 8시간
  },
}));
```

기본 `express-session`은 메모리에 세션을 저장합니다 — 서버 프로세스가
재시작되면(배포, 크래시, Render의 슬립→재기동) 로그인 세션이 전부
날아갑니다. `connect-mongo`로 세션을 이미 쓰고 있는 MongoDB에
저장하면, 서버가 재시작돼도 브라우저의 쿠키(세션 ID)와 DB의 세션
데이터가 그대로 매칭됩니다. 별도 Redis 서버를 새로 두지 않고 기존
MongoDB를 재사용한 이유는, 이 규모에서 세션 저장을 위해 인프라를
하나 더 늘릴 필요가 없다고 판단해서입니다.

`SESSION_SECRET`이 없으면 매 프로세스마다 `randomUUID()`로 임시
값을 쓰도록 폴백을 뒀는데, 이 경우 서버가 재시작되는 순간 예전 서명이
무효화돼 로그인이 풀립니다 — 그래서 이 상황을 콘솔 경고로 명시적으로
알립니다(운영 배포에는 반드시 고정된 `SESSION_SECRET`을 설정).

## 크로스 오리진 쿠키 문제 — `sameSite`, `secure`, `trust proxy`

프론트엔드(Vercel)와 백엔드(Render)가 다른 사이트이기 때문에 겪은
문제 두 가지입니다.

**1. 프록시로 원천 차단** — 1장([[01-시스템-아키텍처]])에서 설명한
대로, 브라우저가 항상 프론트엔드 도메인에만 요청하도록 Next.js가
프록시합니다. 이 덕분에 브라우저 관점의 쿠키는 퍼스트파티가 되어
`sameSite: 'lax'`로도 충분히 동작합니다만, 코드에는 프로덕션에서
`sameSite: 'none'` + `secure: true`도 함께 설정해뒀습니다 — 서버-서버
통신 자체는 문제없지만, 혹시 프록시를 거치지 않고 직접 백엔드
도메인을 호출하는 경로(예: 모바일 앱, 디버깅)에서도 쿠키가 정상
동작하도록 방어적으로 넓힌 설정입니다.

**2. `app.set('trust proxy', 1)`** — Render는 앞단에 Cloudflare 같은
프록시가 있어서, 사용자↔Cloudflare 구간은 HTTPS지만 Cloudflare↔
Render 내부 구간은 HTTP로 전달됩니다. Express 입장에서는 "이 연결이
안전한 HTTPS인지"를 직접 볼 수 없고, 대신 프록시가 실어 보내는
`X-Forwarded-Proto` 헤더를 봐야 합니다. `trust proxy`를 켜지 않으면
Express가 이 헤더를 무시하고 "이 연결은 HTTP다"라고 판단해서,
`cookie.secure: true`인 세션 쿠키를 **아예 `Set-Cookie` 헤더에 싣지
않습니다**(secure 쿠키는 HTTPS에서만 전송 가능하므로). 그 결과
로그인 API 자체는 200을 반환하며 성공하지만, 브라우저에 쿠키가 저장
안 돼서 다음 요청부터는 로그인 안 한 상태로 보이는 미묘한 버그가
생깁니다. `trust proxy: 1`을 설정하면 Express가 `X-Forwarded-Proto`를
신뢰해 이 연결을 올바르게 HTTPS로 인식합니다.

## 테스트에서의 인증 처리

`createApp(sessionMongoUrl)`이 세션 저장소 URL을 파라미터로 받는 것도
이 때문입니다 — 테스트에서는 실제 MongoDB Atlas가 아니라
`mongodb-memory-server`(테스트 프로세스 안에서 뜨는 인메모리
MongoDB)의 주소를 넘겨서, 운영 DB를 전혀 건드리지 않고도
로그인→세션→관리자 API 호출까지 통합 테스트로 검증합니다
([[11-테스트와-CI-CD]] 참고).
