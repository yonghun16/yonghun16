## TL;DR
관리자가 어떤 포맷/크기의 이미지를 올려도, 서버가 **항상 "가장 긴
변이 1600px 이하 + WebP, 품질 82"** 로 통일해서 Cloudflare R2에
저장합니다. 관리자가 매번 이미지를 직접 압축할 필요가 없게 만드는
자동화입니다.

## 전체 경로

```
관리자 브라우저(<input type="file">)
   │  multipart/form-data
   ▼
POST /api/uploads  (requireAdmin으로 보호)
   │
   ├─ multer.memoryStorage()      원본을 디스크에 안 쓰고 메모리 Buffer로만 받음
   │    - 5MB 크기 제한
   │    - mimetype이 image/*가 아니면 즉시 거부
   │
   ├─ reencodeImageToWebp(buffer)  sharp로 리사이즈 + WebP 재인코딩
   │
   └─ PutObjectCommand            재인코딩된 Buffer를 R2에 업로드
        │
        ▼
   응답: { url: `${R2_PUBLIC_URL}/${randomUUID()}.webp` }
```

## 왜 서버에서 재인코딩하는가 (클라이언트에서 압축하지 않고)
- 관리자가 스마트폰 카메라로 찍은 사진을 그대로 올리면 수 MB짜리
  비압축/저압축 이미지가 되기 쉽습니다. 이걸 그대로 저장하면 R2
  저장 공간과 고객 화면의 최초 로딩 시간이 불필요하게 커집니다.
- **서버에서 일괄 처리하면 클라이언트(브라우저/모바일 앱) 코드가
  이미지 압축 로직을 몰라도 됩니다** — 업로드 API 하나만 호출하면
  항상 최적화된 결과를 돌려받습니다. 클라이언트마다(웹 관리자 화면)
  중복 구현할 필요가 없습니다.

## 왜 WebP인가
같은 화질 기준으로 JPEG/PNG보다 파일 크기가 대체로 더 작습니다.
최신 브라우저(Chrome, Safari, Firefox 전부)와 `next/image`가 WebP를
기본 지원해서 호환성 문제가 없습니다.

## 리사이즈 알고리즘 — `sharp`

```ts
export const MAX_IMAGE_DIMENSION = 1600;
export const WEBP_QUALITY = 82;

export async function reencodeImageToWebp(input: Buffer): Promise<Buffer> {
  return sharp(input)
    .resize(MAX_IMAGE_DIMENSION, MAX_IMAGE_DIMENSION, { fit: 'inside', withoutEnlargement: true })
    .webp({ quality: WEBP_QUALITY })
    .toBuffer();
}
```

- **`fit: 'inside'`**: 가로/세로 중 **더 긴 변**이 1600px를 넘지
  않도록 비율을 유지하며 축소합니다(정사각형으로 잘라내는
  `'cover'`가 아니라, 원본 비율을 그대로 유지하는 방식).
- **`withoutEnlargement: true`**: 원본이 이미 1600px보다 작으면
  **확대하지 않습니다**(작은 이미지를 억지로 키우면 화질만
  나빠지고 얻는 게 없음).
- **왜 하필 1600px인가**: 이 이미지들이 실제로 화면에 보이는
  최대 크기(상품 카드, 광고 배너의 최대 표시 폭)가 레티나(2배
  디스플레이) 감안해도 1600px 이내이기 때문입니다. 이보다 큰
  원본을 그대로 저장하는 건 "화면에 보이지도 않을 해상도"를
  저장하는 낭비입니다.
- **왜 품질 82인가**: WebP 품질 80~85 구간이 육안으로 화질 저하가
  거의 안 보이면서 파일 크기를 크게 줄이는, 웹 최적화에서 통상
  쓰이는 절충값입니다.

## 손상된 파일 처리
`sharp`가 이미지가 아니거나 손상된 버퍼를 받으면 예외를 던집니다.
업로드 라우트는 이 예외를 잡아 "이미지 파일을 처리할 수 없습니다"라는
사용자 메시지로 바꿔서 400을 반환합니다 — `sharp`의 원본 에러
메시지를 그대로 노출하지 않고, 무엇이 잘못됐는지 관리자가 이해할 수
있는 말로 감쌉니다.

## 저장 위치 — 왜 R2에 저장하고 MongoDB엔 URL만 두는가
MongoDB는 문서 하나의 크기 제한(16MB)이 있고, 애초에 바이너리 대용량
파일을 저장하는 용도로 최적화돼 있지 않습니다. R2는 오브젝트
스토리지 전용이라 대용량 파일 서빙에 적합하고, `PutObjectCommand`로
업로드한 뒤 **공개 URL 하나만 문자열로** `Product.imageUrl`/
`Ad.imageUrl`에 저장합니다. 실제 이미지 바이트는 고객 브라우저가
R2에서 직접 받아오므로, 백엔드(Render) 서버는 이미지 서빙 부하를
전혀 지지 않습니다.

파일 키는 `${randomUUID()}.webp`로 짓습니다 — 원본 파일명을 그대로
쓰면 한글/공백/특수문자가 URL에 섞이거나, 같은 이름의 파일이 덮어
써지는 충돌이 생길 수 있어 항상 새 UUID를 발급합니다.

## R2 클라이언트 — S3 호환 API 재사용

```ts
export const r2Client = new S3Client({
  region: 'auto',           // R2는 리전 개념이 없음
  endpoint: R2_ENDPOINT,     // Cloudflare가 발급한 R2 엔드포인트
  credentials: { accessKeyId, secretAccessKey },
});
```

Cloudflare R2는 AWS S3와 API 호환을 표방하기 때문에, AWS 공식
SDK(`@aws-sdk/client-s3`)를 그대로 쓰고 `endpoint`만 R2 주소로
바꾸면 됩니다 — R2 전용 SDK를 새로 배울 필요가 없습니다.

## 필수 환경변수가 없으면 즉시 종료
`r2Client.ts`는 모듈이 로드되는 시점(함수 호출이 아니라 `import`
되는 순간)에 `R2_ENDPOINT`/`R2_ACCESS_KEY_ID`/`R2_SECRET_ACCESS_KEY`
가 있는지 확인하고, 없으면 `console.error` 후 `process.exit(1)`로
서버 자체를 띄우지 않습니다. "이미지 업로드를 시도한 순간에야
설정 누락을 알게 되는" 것보다, **서버가 아예 시작되지 않게** 해서
배포 환경변수 설정 실수를 최대한 빨리(배포 직후) 드러내는 방향을
택했습니다. 이 패턴 때문에 백엔드 테스트는 `tests/setupEnv.ts`에서
이 환경변수들에 더미 값을 채워둡니다([[11-테스트와-CI-CD]] 참고).
