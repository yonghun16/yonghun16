읽기만 해서는 안 늘어납니다. 여기 있는 연습은 **정답 코드가 이미 이 저장소에 있다**는 게 특징입니다 — 막히면 참고하되, 먼저 스펙만 보고 스스로 시도해보세요.

## 준비: 연습용 브랜치 만들기
기존 코드를 지우지 말고, 별도 브랜치에서 연습하는 걸 추천합니다.

```bash
git checkout -b study/practice
```

연습 문제마다 관련 파일을 지우거나 내용을 비우고 스스로 채워보세요. 다 하고 나면 `git diff main`으로 원래 코드와 비교해볼 수 있습니다. 다 끝나면 이 브랜치는 머지하지 말고 그냥 두거나 지우면 됩니다.

## 문제 1 (쉬움): 순수 함수부터 — `board.ts`

**목표**: `src/features/bingo-room/utils/board.ts`를 안 보고, 아래 요구사항만으로 처음부터 다시 짜보세요.

- `createEmptyBoard()`: 5x5, 전부 `null`인 배열
- `isBoardValid(board)`: 1~25가 중복 없이 전부 채워졌는지
- `placeNumberOnBoard(board, value, row, col)` / `clearCellOnBoard(board, row, col)`: 특정 칸에 숫자를 놓거나 비움 (원본 배열을 바꾸지 말고 새 배열을 반환할 것 — "불변성")
- `countCompletedLines(board, markedNumbers)`: 가로 5 + 세로 5 + 대각선 2 = 12줄 중 완성된 줄 수

**검증 방법**: 브라우저 없이도 확인할 수 있습니다. `npx tsx` 같은 도구로 직접 실행해보는 스크립트를 짜보세요.

```ts
// 예시 검증 스크립트 아이디어
import { createEmptyBoard, placeNumberOnBoard, countCompletedLines } from "./board";

let board = createEmptyBoard();
// 1~25를 순서대로 채운 뒤
// 특정 숫자들만 marked로 넘겨서 countCompletedLines가 예상한 값을 내는지 확인
```

**막히면**: `src/features/bingo-room/utils/board.ts`의 실제 구현과 비교해보세요. 특히 `countCompletedLines`가 "가로/세로/대각선 좌표 목록"을 어떻게 만드는지(`buildLines` 함수) 눈여겨보세요.

## 문제 2 (중간): 로컬 상태 훅 — `useBingoBoard`

**목표**: 문제 1에서 만든 순수 함수들을 갖고, "숫자를 하나 고른 뒤 빈 칸을 클릭하면 배치되고, 채워진 칸을 클릭하면 비워지는" 훅을 만들어보세요.

**힌트**:
- `useState`로 `board`와 `selectedNumber` 두 개만 있으면 됩니다.
- "클릭한 칸이 이미 채워져 있으면 지운다, 아니면 선택된 숫자를 놓는다"는 분기가 핵심입니다.
- `reset`, `placeAt`, `selectNumber` 세 함수를 `useCallback`으로 감싸보세요. [[01-리액트-패턴]]의 2번을 참고해서, "왜" 감싸야 하는지도 설명할 수 있어야 합니다.

**막히면**: `src/features/bingo-room/hooks/useBingoBoard.ts`.

## 문제 3 (중간): Presence로 "누가 방에 있는지" 보여주기

**목표**: Supabase 프로젝트가 준비돼 있다는 전제로([[Supabase-프로젝트-설정]] 참고), 001 스펙만 보고 아래를 직접 구현해보세요.
- 방에 입장하면 채널을 구독하고 내 닉네임으로 `track()`
- `presence.sync` 이벤트로 현재 참가자 목록을 화면에 표시
- 닉네임이 이미 있으면 입장을 막고 에러 메시지 표시
- 참가자 중 `joinedAt`이 가장 이른 사람을 "방장"으로 표시

**막히면**: `src/features/bingo-room/api/roomChannel.ts`와 `src/features/bingo-room/hooks/useRoomPresence.ts`의 `join()` 함수 앞부분(닉네임 중복 체크까지).

**검증 방법**: `npm run dev`로 두 개 이상의 브라우저 탭(또는 시크릿 창)을 열어 서로 다른 닉네임으로 들어가서, 양쪽 탭에 참가자 목록이 실시간으로 같이 보이는지 확인하세요.

## 문제 4 (어려움): 스펙 순서대로 `useRoomPresence` 늘려나가기

**목표**: 문제 3에서 만든 기초 위에, 002 → 003 → 004 → 005 → 006 스펙을 순서대로 하나씩 구현해보세요. 각 스펙의 "완료 기준"(Test 섹션)을 통과하면 다음으로 넘어가는 방식입니다.

```bash
leanspec view 002-board-setup
leanspec view 003-turn-gameplay
leanspec view 004-game-end-restart
leanspec view 005-chat
leanspec view 006-reconnect-sync
```

각 단계에서 스스로에게 물어볼 질문:
- 이 기능은 **Presence**(지금 상태)로 처리해야 하나, **Broadcast**(방금 일어난 일)로 처리해야 하나?
- 이 판단(예: "게임을 시작해도 되는가")은 **모두가 각자 계산**해도 되는 건가, 아니면 **호스트만** 대표로 해야 하는 건가?
- 서버가 없는데, 이 값을 "누가" 기억하고 있어야 하나?

이 질문들에 스스로 답할 수 있게 되면, [[04-핵심-설계-결정]] 없이도 비슷한 실시간 앱을 설계할 수 있는 겁니다.

## 문제 5 (도전): 스스로 기능을 하나 설계해서 추가하기

정답이 없는 문제입니다. 예시:
- 게임 중 이모지 반응 보내기 (`👍`, `😱` 같은 걸 순간적으로 화면에 띄우기)
- 관전(Spectator) 모드 — 지금은 명시적으로 제외된 기능입니다([[게임흐름]] "2. 입장" 참고)
- 방 목록/최근 방문 기록 (지금은 링크가 있어야만 들어갈 수 있음)

**연습 순서를 이 프로젝트 방식 그대로 따라 해보세요**:
1. LeanSpec으로 새 스펙 작성 (`leanspec create <기능이름>`) — Design/Plan/Test를 먼저 채운다.
2. 구현하면서 스펙과 다르게 짜게 되면, 스펙도 같이 고친다([[04-핵심-설계-결정]]의 6, 7번 항목이 실제로 이렇게 만들어졌습니다 — 처음 스펙엔 없었는데 구현하다 필요해서 추가됨).
3. 다 되면 스펙 상태를 `in-progress` → `complete`로.

이 과정 자체가 "AI와 함께 스펙 기반으로 개발하는 법"을 몸으로 익히는 연습입니다.
