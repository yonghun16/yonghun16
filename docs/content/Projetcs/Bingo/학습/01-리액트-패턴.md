React 공식 문서식 설명이 아니라, **이 코드에서 "왜 여기서 이걸 썼는가"** 위주로 씁니다.

## 1. useState vs useRef — "리렌더가 필요한가?"로 가른다

`useState`는 값이 바뀌면 화면을 다시 그려야 할 때 씁니다. `useRef`는 값은 최신으로 유지해야 하지만 그 값이 바뀌었다고 화면을 다시 그릴 필요는 없을 때 씁니다.

`src/features/bingo-room/hooks/useRoomPresence.ts`를 보면 둘이 섞여 있습니다.

```ts
const [calledNumbers, setCalledNumbers] = useState<number[]>([]);   // 화면에 목록으로 보여줘야 함 → state
const calledNumbersRef = useRef<number[]>([]);                       // 최신 값만 필요 → ref

useEffect(() => {
  calledNumbersRef.current = calledNumbers;                          // state가 바뀔 때마다 ref도 맞춰준다
}, [calledNumbers]);
```

왜 굳이 같은 값을 두 군데(`calledNumbers` state와 `calledNumbersRef`)에 들고 있을까요? 이유는 **클로저(closure)** 때문입니다.

```ts
const timeoutId = setTimeout(() => {
  const remaining = ALL_NUMBERS.filter((n) => !calledNumbersRef.current.includes(n));
  // ...
}, delay);
```

이 `setTimeout` 콜백은 등록된 시점의 `calledNumbers`가 아니라, **실행되는 시점의 최신 값**을 봐야 합니다(그 사이에 다른 숫자가 이미 호출됐을 수 있으니까). 만약 `calledNumbersRef.current` 대신 그냥 `calledNumbers`를 썼다면, 이 콜백은 `setTimeout`이 걸릴 때의 낡은 값을 계속 참조하게 됩니다(리액트의 클로저가 그 시점 값을 "기억"해버리기 때문). 그래서 "이벤트 리스너나 타이머처럼 오래 살아있는 콜백 안에서 최신 값을 읽어야 할 때는 ref를 쓴다"는 패턴이 이 파일 전체에 반복됩니다 (`isHostRef`, `selfPayloadRef`, `boardRef`, `sharedStateRef` 등도 전부 같은 이유).

**기억할 규칙**: 화면에 그릴 값 → `useState`. "지금 이 순간의 최신 값을 나중에 실행될 콜백에서 읽어야 하는" 값 → `useRef`.

## 2. useCallback — 함수의 "정체성"을 고정한다

`src/features/bingo-room/hooks/useBingoBoard.ts`:

```ts
const reset = useCallback(() => {
  setBoard(createEmptyBoard(size));
  setSelectedNumber(null);
}, [size]);
```

`useCallback` 없이 그냥 `const reset = () => {...}`로 썼다면, 컴포넌트가 리렌더될 때마다 `reset`은 **매번 다른 함수**가 됩니다(내용은 같아도 자바스크립트에서 함수는 참조 타입이라 매번 새로 만들어지면 다른 객체입니다). 이게 왜 문제가 되냐면, `src/app/routes/RoomPage.tsx`에서 이렇게 쓰기 때문입니다.

```ts
const { reset: resetBoard } = bingoBoard;

useEffect(() => {
  if (previousStatusRef.current !== "waiting" && roomStatus === "waiting") {
    resetBoard();
  }
  previousStatusRef.current = roomStatus;
}, [roomStatus, resetBoard]);
```

`useEffect`의 두 번째 배열(의존성 배열)에 `resetBoard`가 들어있습니다. 만약 `resetBoard`가 렌더마다 새 함수라면, 이 `useEffect`는 `roomStatus`가 안 바뀌어도 렌더될 때마다 매번 다시 실행됩니다(원치 않는 동작). `useCallback`으로 감싸서 "의존성 배열(`[]`)이 안 바뀌는 한 같은 함수를 재사용"하게 만들면, 이 문제가 사라집니다.

**기억할 규칙**: 함수를 다른 훅의 의존성 배열에 넣거나, 자식 컴포넌트에 props로 넘길 때는 `useCallback`을 고려한다.

## 3. useMemo — "매번 새로 계산하지만, 필요할 때만" 파생 값

`useRoomPresence.ts`:

```ts
const markedNumbers = useMemo(() => {
  const marked = new Set<number>();
  if (!board) return marked;
  const called = new Set(calledNumbers);
  for (const row of board) {
    for (const cell of row) {
      if (cell !== null && called.has(cell)) marked.add(cell);
    }
  }
  return marked;
}, [board, calledNumbers]);

const completedLines = useMemo(
  () => (board ? countCompletedLines(board, markedNumbers) : 0),
  [board, markedNumbers],
);
```

`markedNumbers`(마킹된 칸)와 `completedLines`(완성 라인 수)는 **저장해두는 값이 아니라, `board`와 `calledNumbers`로부터 계산되는 값**입니다. 이런 값을 `useState`로 따로 관리하면 "board가 바뀔 때마다 markedNumbers도 손으로 갱신해야 하고, 깜빡하면 둘이 어긋나는" 버그가 생기기 쉽습니다. `useMemo`는 "이 값은 항상 이 재료들로부터 계산된 결과다"라고 선언하는 방법이고, 재료(`board`, `calledNumbers`)가 안 바뀌면 재계산도 안 합니다(성능 최적화는 덤이고, 핵심은 "항상 최신 상태와 일치함을 보장"하는 것입니다).

**기억할 규칙**: 다른 state/props로부터 계산할 수 있는 값은 별도 state로 만들지 말고 `useMemo`(또는 그냥 렌더 중 계산)로 유도한다.

## 4. Custom Hook으로 책임 나누기

이 프로젝트의 훅들:
- `useBingoBoard` — 내 보드 배치 상태만 담당 (Supabase는 전혀 모름)
- `useCountdownSeconds` — "언제부터 몇 ms 카운트다운"만 계산하는 순수 UI 훅
- `useRoomPresence` — 방/게임 상태 전체(Presence, 모든 broadcast 이벤트) 담당

`useRoomPresence`는 사실 "하나의 Hook은 하나의 역할"이라는 원칙만 보면 너무 큽니다(300줄 넘음). 왜 이렇게 됐는지, 쪼개는 게 더 나았을지는 [[04-핵심-설계-결정]]에서 다룹니다 — 실전에서는 항상 원칙대로 딱 떨어지지 않는다는 것도 배울 부분입니다.

## 5. Controlled Component로 끌어올리기 (Lifting State Up)

`BoardSetupPanel`은 원래 `useBingoBoard()`를 직접 호출하는 컴포넌트였습니다. 그런데 003번(턴 진행) 스펙을 구현하면서 문제가 생겼습니다 — 게임이 시작되면 `BoardSetupPanel`은 화면에서 사라지는데, 마킹을 하려면 "내가 배치한 보드"가 계속 필요했습니다. `BoardSetupPanel` 내부에만 있던 상태는 그 컴포넌트가 사라지면 같이 사라집니다.

해결책은 `useBingoBoard()`를 **상위 컴포넌트(`RoomPage`)로 끌어올리고**, `BoardSetupPanel`은 그 값을 props로만 받는 "그리기 전용" 컴포넌트로 바꾸는 것이었습니다.

```tsx
// RoomPage.tsx
const bingoBoard = useBingoBoard(safeRoomId, boardSize);   // 여기서 한 번만 호출
// ...
<BoardSetupPanel
  board={bingoBoard.board}
  onCellClick={handleCellClick}
  // ...
/>
```

**기억할 규칙**: 어떤 상태가 "지금 보이는 화면"보다 더 오래 살아있어야 한다면, 그 상태를 들고 있는 컴포넌트가 아니라 상위(부모) 컴포넌트로 옮긴다.
