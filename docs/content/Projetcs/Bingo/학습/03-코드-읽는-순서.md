`src/`를 위에서 아래로 훑으면 이해가 안 됩니다. 아래 순서대로 읽으세요. 각 단계에서 "이 파일이 왜 이 모양인지"까지 [[04-핵심-설계-결정]]과 연결해뒀습니다.

## 1단계: 앱이 켜지는 순서 (제일 쉬움)
```
src/main.tsx → src/app/App.tsx → src/app/Router.tsx → src/app/routes/LandingPage.tsx
```
- `main.tsx`: React를 `#root`에 렌더링하는 진입점. 특별한 로직 없음.
- `App.tsx`: `Providers`(지금은 사실상 아무것도 안 함)로 `Router`를 감쌈.
- `Router.tsx`: `/`(LandingPage), `/room/:roomId`(RoomPage) 두 라우트만 있음.
- `LandingPage.tsx`: "방 만들기" 버튼 → `crypto.randomUUID()`로 방 ID 생성 → `/room/{id}`로 이동. Supabase를 전혀 모름(연결이 필요 없는 화면이라서).

여기서 배울 것: 라우팅/조립(`app/`)과 실제 기능(`features/`)이 분리돼 있다는 것.

## 2단계: 연결 준비
```
src/config/env.ts → src/lib/supabase.ts
```
[[02-Supabase-Realtime-핵심개념]] 1번 참고. 둘 다 "실제로 필요해질 때만" 초기화하는 지연 패턴.

## 3단계: 데이터 모양부터 파악
```
src/features/bingo-room/types/domain.ts → src/features/bingo-room/types/events.ts
```
코드를 읽기 전에 **어떤 데이터가 오가는지**부터 알면 나머지가 쉬워집니다.
- `domain.ts`: `Room`, `Player`, `ChatMessage`, `RoomPresencePayload` — 이 앱이 다루는 "명사"들.
- `events.ts`: `GameStartedPayload`, `NumberCalledPayload`, `GameOverPayload` 등 — Broadcast로 오가는 "사건"들.

`RoomPresencePayload`에 왜 `roomStatus`, `completedLines`까지 들어있는지 의아하다면 [[04-핵심-설계-결정]]을 먼저 봐도 됩니다.

## 4단계: 통신의 최하단 레이어
```
src/features/bingo-room/api/roomChannel.ts
```
[[02-Supabase-Realtime-핵심개념]] 2~5번에서 이미 이 파일을 다 봤습니다. 여기 있는 5개 함수(`createRoomChannel`, `leaveRoomChannel`, `trackPresence`, `untrackPresence`, `broadcast`)가 이 앱의 모든 네트워크 동작의 기반입니다. `createRoomChannel`은 채널 객체만 만들고 `.subscribe()`는 호출하지 않는다는 점을 눈여겨보세요 — 이유는 02번 문서 5번 참고.

## 5단계: 제일 크고 중요한 파일 — `useRoomPresence.ts`
```
src/features/bingo-room/hooks/useRoomPresence.ts (300줄 이상)
```
한 번에 다 이해하려 하지 말고, **스펙 번호 순서대로** 나눠서 읽으세요. 실제로 이 파일도 그 순서로 커졌습니다.

| 읽을 부분 | 대응 스펙 |
|---|---|
| `join()`의 닉네임 중복/정원 체크, `host` 계산 | `001-room-lifecycle` |
| `setReady`, `applyGameStarted`, "전원 준비 완료" effect | `002-board-setup` |
| `callNumber`, `applyNumberCalled`, 10초 타임아웃 effect, `markedNumbers`/`completedLines` | `003-turn-gameplay` |
| `applyBingoCompleted`, `finalizeGameOver`, `revealOwnBoard`, `restartGame` | `004-game-end-restart` |
| `sendChatMessage`, `applyChatMessage` | `005-chat` |
| `applyStateSync`, `request-state`/`state-sync` 관련 부분, `hasReconnectTimedOut` | `006-reconnect-sync` |

각 스펙 문서(`leanspec view 001-room-lifecycle` 등)를 옆에 띄워두고, "이 스펙이 요구하는 걸 코드의 어느 줄이 하고 있나"를 짝지어보는 게 제일 빠른 이해 방법입니다.

## 6단계: 보드 로직과 로컬 저장
```
src/features/bingo-room/utils/board.ts
src/features/bingo-room/hooks/useBingoBoard.ts
src/features/bingo-room/utils/roomStorage.ts
```
`board.ts`는 Supabase를 전혀 모르는 **순수 함수**만 모아뒀습니다(보드 생성, 배치, 줄 완성 판정). 이런 함수들은 브라우저 없이도 테스트할 수 있습니다 — 실제로 이 프로젝트를 만들 때도 `countCompletedLines` 같은 함수를 스크립트로 직접 돌려서 검증했습니다([[05-직접-구현해보기]]에서 같은 걸 해봅니다).

## 7단계: 화면 부품들 (작은 것 → 큰 것)
```
BingoBoard.tsx (그리드 하나 그리기)
  → NumberPalette.tsx (세팅 단계 숫자 버튼들)
  → BoardSetupPanel.tsx / TurnGameplayPanel.tsx / GameOverPanel.tsx (한 화면 단계씩 조합)
  → RoomLayout.tsx / ChatPanel.tsx / ChatToastLayer.tsx / ParticipantList.tsx / NicknameEntryForm.tsx / InviteLinkBox.tsx
```
각 컴포넌트는 "하나의 책임"만 갖게 나뉘어 있습니다. 예를 들어 `BingoBoard`는 그리기만 하고 클릭 처리 로직은 모름(`onCellClick` prop만 받음) — 그래서 세팅 화면(내 보드, 클릭 가능)과 게임 화면(칸을 직접 눌러 숫자 호출, 마킹 표시)에 똑같이 재사용됩니다. 게임 진행 화면에는 원래 별도 숫자 호출판(`NumberCallPad`)이 있었지만, "내 보드 칸을 직접 누르는" 방식으로 바뀌면서 삭제됐습니다 — 같은 정보를 두 군데(보드 + 별도 패드)에 중복해서 보여줄 필요가 없다고 판단한 것입니다.

## 8단계: 마지막으로 전부 조립하는 곳
```
src/app/routes/RoomPage.tsx
```
이 파일을 마지막에 보는 이유: `useRoomPresence`, `useBingoBoard`, 그리고 위 7단계의 모든 컴포넌트를 다 알아야 이 파일이 "무엇을 조립하고 있는지" 이해가 되기 때문입니다. `roomStatus`(`waiting`/`playing`/`ended`) 값에 따라 어떤 화면을 보여줄지 분기하는 게 이 파일의 핵심입니다.
