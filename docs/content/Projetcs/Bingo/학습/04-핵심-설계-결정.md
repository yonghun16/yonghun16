코드만 봐서는 "왜 굳이 이렇게?"라는 생각이 드는 부분들이 있습니다. 여기서는 그 "왜"를 다룹니다. 각 항목은 실제로 이 프로젝트를 만들면서 순서대로 부딪혔던 문제들입니다.

## 1. 서버가 없는데, 턴 타이머는 누가 관리하나? → "호스트" 개념

서버가 없으면 "시간 초과됐으니 자동으로 다음 사람 차례로 넘긴다" 같은 판단을 **누군가 대표로** 해야 합니다. 이 프로젝트는 "방에 가장 먼저 들어온 사람"을 호스트로 정하고, 호스트의 클라이언트가 이 역할을 맡깁니다.

```ts
const host = players.reduce<Player | null>(
  (earliest, player) => (!earliest || player.joinedAt < earliest.joinedAt ? player : earliest),
  null,
);
```

**모든 클라이언트가 이 계산을 각자 독립적으로 합니다.** 서버가 "누가 호스트다"라고 알려주는 게 아니라, 다들 같은 Presence 목록을 보고 있으니 같은 계산식이면 같은 답이 나온다는 원리입니다. 호스트가 연결을 끊으면 그 사람이 Presence에서 사라지고, 남은 사람 중 `joinedAt`이 가장 이른 사람이 **자동으로** 새 계산 결과가 됩니다 — 별도로 "호스트 인수인계" 이벤트를 보낼 필요가 없습니다.

**트레이드오프**: 호스트 클라이언트가 버그가 있거나 악의적이면 게임 진행에 영향을 줄 수 있습니다. 지인 몇 명이 하는 캐주얼 게임이라는 전제(`docs/decisions/0001-supabase-realtime-통신.md` 참고)로 감수한 선택입니다.

## 2. 수동 호출과 자동 호출이 겹치면? → `turnSeq`로 경합 해결

턴 유저가 막 숫자를 누른 순간, 하필 호스트의 10초 타이머도 거의 동시에 끝나서 "시간 초과 자동 호출"을 보내버릴 수 있습니다. 그러면 같은 턴에 대해 **서로 다른 두 개의 `number-called`**가 돌아다니게 됩니다.

해결책은 매 턴마다 1씩 증가하는 일련번호 `turnSeq`를 붙이고, "이 턴 번호에 대해 가장 먼저 도착한 것만 인정"하는 규칙입니다.

```ts
const applyNumberCalled = useCallback((payload: NumberCalledPayload) => {
  if (payload.turnSeq <= appliedTurnSeqRef.current) return; // 이미 처리한 턴 (경합/중복)
  appliedTurnSeqRef.current = payload.turnSeq;
  // ...
}, []);
```

두 번째로 도착한 이벤트는 `payload.turnSeq <= appliedTurnSeqRef.current` 조건에 걸려서 조용히 무시됩니다. **모든 클라이언트가 같은 규칙으로 판단**하므로, 누가 먼저 도착했는지만 다를 뿐 최종적으로 다들 같은 숫자를 채택하게 됩니다(네트워크 지연으로 순서가 살짝 달라져도 큰 문제가 안 되는 이유).

## 3. 카운트다운을 `setInterval`로 직접 돌리지 않는 이유

턴 타이머를 각자 클라이언트에서 `setTimeout(..., 10000)`으로 새로 시작하면, 호스트가 바뀌는 순간(연결이 끊기고 승계되는 그 타이밍) 새 호스트는 "10초가 얼마나 지났는지" 알 방법이 없습니다. 그래서 "언제 턴이 시작됐는지"(`turnStartedAt`, 타임스탬프)를 이벤트에 실어 보내고, 모두가 `turnStartedAt + 10초`를 기준으로 남은 시간을 계산합니다.

```ts
// useCountdownSeconds.ts
return Math.max(0, Math.ceil((startedAt + durationMs - now) / 1000));
```

이렇게 하면 새 호스트가 이어받아도, 원래 시작 시각을 그대로 알고 있으니 타이머가 처음부터 다시 시작되지 않습니다. **"경과 시간을 스스로 세지 말고, 기준 시각으로부터 계산하라"**는 건 분산 시스템에서 자주 쓰이는 패턴입니다.

## 4. 완성 라인 "개수"는 왜 Presence로 공유하나?

보드 내용(어디에 몇 번을 놨는지)은 게임이 끝나기 전까진 아무에게도 안 보여줘야 합니다(부정행위 방지 목적이 아니라 원래 빙고 게임의 규칙이 그렇습니다). 하지만 "누가 몇 줄 완성했는지"는 게임 화면에 항상 보여줘야 하는 정보입니다(게임흐름.md UI 요구사항). 그래서 `RoomPresencePayload`에 `completedLines` 숫자만 넣어서 공유하고, 실제 보드 배열은 절대 넣지 않습니다.

```ts
export interface RoomPresencePayload {
  nickname: string;
  isReady: boolean;
  joinedAt: number;
  roomStatus: "waiting" | "playing" | "ended";
  completedLines: number;   // 개수만. board는 없음.
}
```

**배울 점**: "정보를 어디까지 공개할지"는 데이터 모델을 설계할 때 처음부터 정해야 하는 결정입니다. "일단 다 넣고 나중에 가리자"가 아니라 "필요한 만큼만 넣는다"는 원칙입니다.

## 5. `game-over`에 우승자 정보만 있고 보드가 없는 이유

4번과 같은 이유로, 호스트조차 다른 사람의 보드를 모릅니다. 그래서 게임이 끝났을 때 "모든 참가자의 보드를 공개"하려면 2단계가 필요합니다.

1. 호스트가 우승자 **id만** 담아 `game-over`를 보낸다.
2. `game-over`를 받은 **각자**가 그제서야 자기 보드를 `board-revealed`로 보낸다.

```ts
const applyGameOver = useCallback((payload: GameOverPayload) => {
  // ...
  setWinnerIds(payload.winnerIds);
  revealOwnBoard();   // 여기서 내 보드를 공개
}, [revealOwnBoard]);
```

호스트가 "다른 사람 보드까지 모아서 한 번에 보내는" 중앙집중적 설계가 아니라, "각자 자기 것만 책임지고 공개하는" 분산적 설계입니다. 서버가 없는 아키텍처에서는 이런 식으로 "누가 어떤 정보를 갖고 있는가"를 항상 의식해야 합니다.

## 6. 새로고침하면 왜 내 보드가 사라지나 → `localStorage`

Realtime으로 방/게임 상태(누가 있는지, 몇 번이 불렸는지 등)는 복구할 수 있습니다 — 다른 사람들이 아직 그 정보를 갖고 있으니까요. 하지만 **내 보드 배치는 애초에 아무에게도 공유한 적이 없어서**, 새로고침하면 이 브라우저 메모리에서 사라지는 순간 우주에서 완전히 사라집니다.

그래서 내 보드와 닉네임만 예외적으로 `localStorage`에 저장해둡니다(`roomStorage.ts`). 이건 Realtime과 무관한, 순수히 "이 브라우저가 스스로를 위해 남겨두는 메모"입니다.

```ts
export function useBingoBoard(roomId: string, size: BoardSize): UseBingoBoardResult {
  const [board, setBoard] = useState<BoardGrid>(() => loadSavedBoard(roomId) ?? createEmptyBoard(size));
  useEffect(() => {
    saveBoard(roomId, board);
  }, [roomId, board]);
  // ...
}
```

(`size`는 방 만들기 때 고른 보드 크기(3~7)로, 001 스펙에서 `?size=` 쿼리 파라미터로 전달된다 — 이 문서의 다른 예시 코드는 보드 크기가 5x5로 고정이던 시절 기준이라 `size` 매개변수가 없을 수 있다.)

**배울 점**: "실시간 동기화"와 "로컬 영속성"은 다른 문제입니다. 여러 사람과 공유해야 하는 상태는 Realtime으로, 나만 알면 되는 상태는 `localStorage`로 — 이렇게 책임을 나누는 감각이 중요합니다.

## 7. 재접속한 사람이 "원래 참가자"인지 "낯선 사람"인지 어떻게 구분하나

게임이 이미 시작된 방에 누군가 들어오려고 합니다. 두 가지 경우가 있습니다.
- 원래 있던 사람이 새로고침해서 돌아오는 경우 → 받아줘야 함
- 링크만 갖고 있는 생판 남이 진행 중인 게임에 끼어들려는 경우 → 막아야 함

두 경우 모두 "같은 닉네임이 Presence에 없다"는 점은 똑같습니다(원래 있던 사람도 새로고침하면 Presence에서 사라졌다가 다시 들어오니까). 그래서 닉네임 중복 체크만으로는 구분이 안 됩니다.

해결책은 게임 시작 시점에 고정된 `turnOrder`(참가자 id 목록)를 활용하는 것입니다. 재접속을 시도하는 클라이언트는 다른 클라이언트에게 `request-state`로 현재 상태를 물어보고, 응답에 담긴 `turnOrder`에 자기 닉네임이 있는지 확인합니다.

```ts
const isRecognizedReturningPlayer = payload.turnOrder?.includes(nickname) ?? false;
if (!isRecognizedReturningPlayer) {
  leaveRoomChannel(channel);
  resolve({ ok: false, reason: "already-started" });
  return;
}
```

**배울 점**: "지금 이 순간의 상태"(Presence)만으로 판단이 안 될 때는, "과거에 고정된 사실"(게임 시작 시의 참가자 명단)을 같이 봐야 할 수 있습니다.
