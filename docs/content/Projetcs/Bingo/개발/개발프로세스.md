전체 스펙은 [[게임흐름]] 참고. 아래 0~8단계는 MVP까지의 원래 계획이고, 실제로는 전부 완료됐다 — 완료 이후 추가된 작업은 맨 아래 "9단계"를 참고.

## 전체 구조 요약

| 영역 | 스택 | 배포 |
|---|---|---|
| 프론트엔드 | Vite + React + TypeScript + React Router + Tailwind | Vercel (PWA로 설치 가능) |
| 실시간 인프라 | Supabase Realtime (Broadcast + Presence, 별도 서버 코드 없음) | Supabase 관리형 프로젝트 |

**핵심 원칙**: 게임 상태(참가자, 보드, 호출 숫자, 턴, 승패)의 원본 소스는 각 클라이언트다. Supabase Realtime은 broadcast 이벤트를 방 전체에 중계만 하고, 승패 판정이나 턴 관리 같은 로직은 클라이언트(대부분은 방장/호스트 클라이언트)가 계산한다. 자세한 원칙은 [[게임흐름]]의 "실시간 동기화 원칙" 참고.

별도 백엔드 서버가 없으므로 프론트/백엔드 트랙을 나눠 병행할 필요가 없다. 아래 순서대로 하나의 트랙으로 진행한다.

---

## 0단계: Broadcast/Presence 이벤트 명세 확정 (선행 작업)

본격적인 구현 전에 아래를 문서/타입으로 먼저 고정한다. (`types/`에 타입으로도 정의)

- Broadcast 이벤트 이름 목록 (`set-board`, `game-started`, `call-number`, `number-called`, `bingo-completed`, `game-over`, `chat-message`, `restart-game`, `request-state`/`state-sync` 등)
- 각 이벤트의 payload 타입
- Presence 메타데이터 구조 (`nickname`, `isReady`, `joinedAt` 등)와 방장(호스트) 판단 규칙

> 모든 클라이언트가 동일한 코드로 동작하므로, 이 명세가 "계약서" 역할을 한다. 변경이 필요하면 클라이언트 코드 전체(특히 호스트 전용 로직)에 동일하게 반영한다.

---

## 1단계 - 라우팅 + 화면 레이아웃 (Supabase 연동 없이 목업으로 진행 가능)
- [x] React Router 세팅: `/`(랜딩), `/room/:roomId`(방)
- [x] 방 만들기 버튼 → 클라이언트에서 생성한 roomId로 이동
- [x] 좌(빙고판) / 우(채팅) 2분할 레이아웃 컴포넌트
- [x] 닉네임 입력 화면
- [x] **완료 기준**: Supabase 연결 없이도 화면 흐름(랜딩→닉네임 입력→방 화면)이 눈으로 확인 가능

## 2단계 - Supabase 연동 기반 마련
- [x] `lib/supabase.ts`: Supabase 클라이언트 단일 인스턴스
- [x] `features/bingo-room/api/`: `bingo-room-{roomId}` 채널 구독/구독 해제, Presence 설정
- [x] `useRoomPresence` 훅: 참가자 목록, 인원수, 방장(호스트) 여부 계산
- [x] 정원(5명) 초과, 이미 시작된 방 입장 차단 로직(Presence 조회 기반)
- [x] **완료 기준**: 여러 브라우저 탭으로 실제 방 입장/퇴장이 Presence로 동기화되고, 정원 초과·시작된 방 입장 시 에러 안내가 뜸

## 3단계 - 빙고판 세팅 UI + 로직
- [x] 보드 컴포넌트, 1~N 숫자 배치 UI (숫자 먼저/칸 먼저 두 가지 순서 모두 지원, "무작위로 채우기" 버튼도 추가)
- [x] 보드 유효성(중복/누락) 로컬 검증
- [x] 배치 완료 시 Presence 메타데이터(`isReady: true`)로 반영
- [x] 참가자별 준비 상태 표시
- [x] 호스트: 전원 준비 완료(Presence 기준) 감지 시 `game-started` broadcast + 턴 순서 계산(Presence 입장 시각 기준)
- [x] **완료 기준**: 여러 탭에서 전원 준비 완료 시 게임 시작 화면으로 자동 전환되고, 모든 탭에서 동일한 턴 순서가 계산됨

## 4단계 - 게임 진행 화면 (턴 / 타이머 / 호스트 로직)
- [x] 내 턴 여부 표시 + 10초 카운트다운 UI (원형 뱃지, 3초 이하면 강조)
- [x] 숫자 선택 UI — 별도 숫자판 대신 내 빙고판 칸을 직접 눌러 호출 (턴일 때만 활성화, 이미 호출된 숫자는 비활성화)
- [x] 호스트: 턴 타이머 관리, 시간 초과 시 남은 숫자 중 랜덤 자동 호출 → `number-called` broadcast(`auto: true`)
- [x] `number-called` 수신 시 전원의 보드 로컬 마킹 + 완성 라인 수 재계산
- [x] 보드 크기별 필요 줄 수 완성 시 `bingo-completed` broadcast
- [x] 호스트: 같은 라운드의 `bingo-completed`를 짧은 유예 시간 동안 모아 동시 달성 판정 → `game-over` broadcast
- [x] 호스트가 연결을 끊으면 다음 순번(Presence 입장 시각 기준)이 자동으로 호스트 역할을 이어받는지 확인
- [x] **완료 기준**: 여러 브라우저 탭으로 방생성→세팅→턴 진행→우승자 결정까지 풀 게임 1회를 오류 없이 완주, 호스트 탭을 강제로 닫아도 게임이 계속 진행됨

## 5단계 - 게임 종료 및 재시작
- [x] `game-over` 수신 시 우승자 배너 + 전체 참가자 보드 공개 뷰 (우승자 보드는 황금색으로 강조)
- [x] "다시 하기" 버튼 → `restart-game` broadcast, "새 게임 만들기" 버튼 → 타이틀 화면으로 이동
- [x] `restart-game` 수신 시 로컬 상태 초기화 후 세팅 단계로 복귀
- [x] **완료 기준**: 종료 후 재시작 시 이전 라운드 데이터가 모든 탭에서 남지 않고 완전히 초기화됨

## 6단계 - 채팅 UI
- [x] 메시지 리스트 + 입력창 (모바일은 플로팅 버튼 + 반투명 바텀시트로 여닫음)
- [x] 닉네임/타임스탬프 표시, `chat-message` broadcast 송수신
- [x] 새 메시지를 화면 상단 토스트로도 알림
- [x] **완료 기준**: 대기실/게임 중 채팅 송수신 UI 정상 동작

## 7단계 - 재접속/새로고침 동기화
- [x] `request-state` broadcast: 새로고침 등으로 상태를 잃은 클라이언트가 현재 상태 요청
- [x] 다른 클라이언트(주로 호스트)가 `state-sync`로 응답
- [x] **완료 기준**: 게임 중간에 새로고침해도 몇 초 내에 현재 상태로 복구됨

## 8단계 - 배포
- [x] Supabase 프로젝트 생성, Realtime 채널 사용량/요금 한도 확인
- [x] `vite build`
- [x] Vercel 배포, Supabase URL/anon key를 환경변수로 분리
- [x] 별도 게임 서버 배포 불필요(백엔드 프로세스, PM2, WebSocket 리버스 프록시 설정 없음)

## 9단계 - MVP 이후 추가된 개선 (배포 이후 진행)
- [x] 보드 크기 선택(3x3/4x4/5x5/6x6/7x7)과 초대 링크 `?size=` 쿼리 파라미터 전달
- [x] `vercel.json` SPA rewrite — 초대 링크로 직접 접속 시 404 나던 문제 수정
- [x] 카톡 등 링크 공유 미리보기(`middleware.ts`) — 방장 닉네임·보드 크기가 반영된 og:image 카드
- [x] `vite-plugin-pwa`로 "홈 화면에 추가" 설치 지원
- [x] 타이틀 화면 + 게임 화면 전체 다크 테마(slate-950~900 + emerald) 리디자인
- [x] 게임 종료 화면 우승자 보드 황금색 강조
- [x] 초대 링크를 "복사 버튼 + 토스트" 방식으로 개편 (항상 보이던 URL 입력창 제거)
- [x] 잘못된 주소 접속 시 안내 페이지(`NotFoundPage`) 추가
- [ ] 버그 수정: 호스트가 우승(특히 공동 우승)할 때 본인이 집계에서 누락되던 문제 — Supabase broadcast self-echo가 꺼져있어 자기 자신에게 온 `bingo-completed`를 못 받던 게 원인, 수정 완료(체크박스는 "회귀 테스트 계속 필요"의 의미로 비워둠)

## 통합 테스트 체크리스트

- [x] 5명 동시 입장 후 6번째 유저 입장 거부되는지
- [x] 보드 세팅 중 한 명이라도 미완료면 게임이 시작 안 되는지
- [x] 턴 시간 초과 시 호스트의 자동 호출이 정상 작동하는지
- [x] 게임 중간에 한 명이 접속 종료해도 나머지 인원으로 게임이 계속되는지
- [x] 호스트가 접속 종료해도 다음 순번이 호스트 역할(타이머/승자 확정)을 이어받는지
- [x] 보드 크기별 필요 줄 수 완성 시점에 즉시 종료되고 전원 보드가 공개되는지
- [x] 재시작 시 이전 라운드 상태가 남지 않는지
- [x] 게임 중 새로고침한 클라이언트가 `request-state`로 정상 복구되는지
- [x] 호스트가 우승(단독/공동)해도 본인이 우승자 목록에 정상 포함되는지 (회귀 테스트, 브라우저로 직접 재현해 확인함)

## 참고: 로컬 개발 시 Supabase 프로젝트 준비

별도 백엔드 트랙이 없으므로 목업 서버를 따로 만들 필요는 없다. 대신 개발 초반(0~1단계)에 무료 Supabase 프로젝트를 하나 만들어 Realtime을 활성화해두면, 2단계부터 바로 실제 채널에 붙여볼 수 있다. 팀/개인 개발 환경 간에는 `.env`로 Supabase URL/anon key만 분리하면 된다. 프로젝트 생성부터 `.env` 작성까지 단계별 절차는 [[Supabase-프로젝트-설정]] 참고.
